# 작업 지시서: 드래그 도중 Ctrl 판정을 훅과 키 상태의 합집합으로 바꾼다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

건드리는 파일은 `src/menu_bar.cpp`와 `src/menu_bar.hpp`입니다. `src/desktop_toggle.*`는 건드리지 않습니다.

**바탕 화면 전환 자체는 이미 동작합니다**(`FIX-CONCEAL-LIST-MERGE.md` 4-3절). 이번에 고치는 것은 그 전환을 부르는 **감지부**이고, 남은 증상 하나뿐입니다.

---

## 1. 사용자가 겪은 것

2026-09-06 21:55 시험 결과입니다.

| 순서 | 결과 |
| --- | --- |
| Ctrl을 **먼저** 누르고 드래그를 시작한다 | 전환된다 |
| 드래그를 **먼저** 시작하고 Ctrl을 누른다 | 전환되지 않는다 |

---

## 2. 로그와 코드로 좁힌 원인

### 2-1. 뜸이 무르익기 전에 감시가 꺼졌습니다

```
21:55:32.123 [peek] watch msg      ← 훅이 Ctrl 눌림을 보았다
21:55:32.123 [peek] watch on=1
21:55:32.463 [peek] corner in=1 x=5119 y=0 right=5120
21:55:32.463 [peek] dwell arm      ← 뜸 시작. 120밀리초 뒤에 터져야 한다
21:55:32.519 [peek] watch on=0     ← 56밀리초 만에 감시가 꺼졌다
```

뜸이 터지려면 120밀리초가 필요한데 **56밀리초 만에 `StopCornerWatch`가 뜸 타이머까지 죽였습니다.** `dwell fire`가 없고 `conceal`도 없습니다. 이것이 사용자가 본 "전환되지 않음"입니다.

바로 뒤인 21:55:33에는 같은 자리에서 `dwell arm` → `dwell fire` → `conceal n=2 total=5`가 정상으로 이어졌습니다. **코드가 늘 실패하는 것이 아니라 특정 순간에만 눈이 머는 것입니다.**

### 2-2. 감시를 끄는 경로는 단 하나입니다

`src/menu_bar.cpp`에서 `StopCornerWatch()`를 부르는 곳은 **497줄 하나뿐입니다.** 코너 감시 타이머 안이고 조건은 이렇습니다.

```cpp
if (wparam == kCornerWatchTimerId) {
  if ((GetAsyncKeyState(VK_CONTROL) & 0x8000) == 0) {
    g_ctrl_held = false;
    StopCornerWatch();
    return 0;
  }
```

곧 21:55:32.519에 **`GetAsyncKeyState(VK_CONTROL)`이 0을 돌려주었다는 뜻입니다.** 다른 해석의 여지가 없습니다.

### 2-3. 그런데 같은 순간 훅은 Ctrl을 보고 있었습니다

396밀리초 전인 21:55:32.123에 `watch msg`가 남았습니다. 이 줄은 저수준 훅이 Ctrl **눌림 전이**를 보았을 때만 나옵니다.

두 관측이 어긋납니다.

| 관측자 | 21:55:32 구간의 판정 |
| --- | --- |
| 저수준 키보드 훅 | Ctrl이 눌렸다 |
| `GetAsyncKeyState(VK_CONTROL)` | Ctrl이 눌리지 않았다 |

**어느 쪽이 물리적 진실인지는 이 지시서가 단정하지 않습니다.** 다만 훅이 본 것을 우리가 스스로 버리고 있다는 사실은 확정입니다.

### 2-4. 지금 구조가 한쪽만 믿게 되어 있는 내력

두 번 방향을 바꾼 이력이 있습니다.

1. 처음에는 훅이 기억하는 `g_ctrl_held`를 믿었습니다. 훅이 키 뗌을 놓치면 상태가 **참인 채로 굳어** 감시가 영영 꺼지지 않았습니다.
2. 그래서 커밋 `2bfe4c7`("드래그 중 Ctrl 판정을 훅 사건이 아니라 실제 키 상태로 바꾼다")에서 `GetAsyncKeyState` 하나만 믿게 바꿨습니다. 이번에는 **거짓으로 0을 돌려주는** 경우에 눈이 멉니다.

**두 관측자가 서로 반대 방향으로 틀립니다.** 훅은 거짓 참(굳음)을 내고, `GetAsyncKeyState`는 거짓 거짓(순간적인 0)을 냅니다. 그러므로 어느 하나를 고르는 한 이 문제는 계속 자리만 옮깁니다.

## 3. 고칠 것

### 3-1. 판정을 합집합으로 바꾸고, 훅의 굳음만 따로 막습니다

`MenuBar`에 판정 함수 하나를 새로 두십시오.

```cpp
// Ctrl 이 눌려 있는가.
//
// 관측자가 둘이고 서로 반대 방향으로 틀린다. 훅은 키 뗌을 놓치면 참인 채로
// 굳고, GetAsyncKeyState 는 눌려 있는데도 0 을 돌려주는 순간이 있다.
// 그래서 합집합으로 보되, 훅만 참인 상태가 오래 이어지면 굳은 것으로 보고
// 훅 쪽을 버린다.
bool CtrlHeld();
```

판정 규칙입니다.

```
async = (GetAsyncKeyState(VK_CONTROL) & 0x8000) != 0

async 가 참이면
    ctrl_hook_only_since_ = 0
    참을 돌려준다

async 가 거짓이고 g_ctrl_held 가 거짓이면
    ctrl_hook_only_since_ = 0
    거짓을 돌려준다

async 가 거짓이고 g_ctrl_held 가 참이면            // 두 관측이 어긋난 구간
    ctrl_hook_only_since_ 가 0 이면 지금 시각을 넣는다
    어긋난 시간이 kCtrlHookGraceMs 를 넘었으면
        g_ctrl_held = false                        // 굳은 것으로 보고 버린다
        ctrl_hook_only_since_ = 0
        로그: ctrl hook stale
        거짓을 돌려준다
    아니면 참을 돌려준다
```

새 멤버와 상수입니다.

```cpp
ULONGLONG ctrl_hook_only_since_ = 0;              // menu_bar.hpp
constexpr ULONGLONG kCtrlHookGraceMs = 600;       // menu_bar.cpp 익명 네임스페이스
```

시각은 `GetTickCount64()`로 재십시오.

**600밀리초의 근거입니다.** 막아야 할 구멍은 2-1절에서 관측된 56밀리초짜리 어긋남이고, 뜸이 120밀리초입니다. 여유를 다섯 배로 두면 충분합니다. 반대로 훅이 굳었을 때 감시가 600밀리초 더 도는 비용은 30밀리초 타이머 스무 번이므로 무시할 만합니다. **걸쇠와 뜸이 그대로 있으므로 이 구간에 화면이 멋대로 바뀌지 않습니다.**

### 3-2. 두 호출 지점을 새 판정으로 바꿉니다

**코너 감시 타이머**(497줄 근처)

```cpp
if (wparam == kCornerWatchTimerId) {
  if (!CtrlHeld()) {
    StopCornerWatch();
    return 0;
  }
```

`g_ctrl_held = false;` 줄은 지우십시오. 굳음 처리는 이제 `CtrlHeld()` 안에서만 합니다. **두 곳에서 같은 전역을 건드리면 어느 쪽이 껐는지 알 수 없게 됩니다.**

**예비 폴링**(489줄 근처)

```cpp
if (wparam == kCtrlPollTimerId) {
  if (CtrlHeld() && !corner_watch_on_) {
    StartCornerWatch();
  }
  return 0;
}
```

이 자리도 바꿔야 합니다. 그러지 않으면 훅이 눌림을 본 뒤 `PostMessage`가 어떤 이유로 유실되었을 때 예비 감시가 여전히 눈이 멉니다.

`DesktopPeekWanted()`의 `GetAsyncKeyState`도 같은 이유로 `CtrlHeld()`로 바꾸십시오.

### 3-3. 어긋남을 한 줄로 남깁니다

원인을 다음 시험에서 확정하기 위한 기록입니다. **`CtrlHeld()` 안에서 어긋남이 시작될 때 딱 한 줄만 남기십시오.**

```
[peek] ctrl split async=0 hook=1 lbtn=%d
```

`lbtn`은 `(GetAsyncKeyState(VK_LBUTTON) & 0x8000) != 0`입니다. 드래그 중인지 가르는 값입니다.

**어긋남이 이어지는 동안에는 다시 남기지 마십시오.** `ctrl_hook_only_since_`가 0에서 값으로 바뀌는 순간에만 남기면 됩니다. 30밀리초 타이머이므로 매 틱 남기면 로그가 폭주합니다.

굳은 것으로 판정해 훅을 버릴 때 `ctrl hook stale` 한 줄을 더 남기십시오.

**이 두 줄로 다음이 갈립니다.**

1. `ctrl split ... lbtn=1`이 드래그마다 나오고 그 뒤에 `dwell fire`와 `conceal`이 이어진다 → **드래그 중 `GetAsyncKeyState`가 거짓으로 0을 낸다는 것이 확정되고, 증상도 해소된 것입니다.**
2. `ctrl split`이 아예 안 나오는데 증상이 남는다 → 원인이 Ctrl 판정이 아니라 다른 데 있습니다. 그때 다시 잽니다.
3. `ctrl hook stale`이 자주 나온다 → 유예가 짧거나 훅이 실제로 자주 굳는 것입니다. 값을 다시 정합니다.

## 4. 검증

### 4-1. 빌드

Release 빌드가 경고 없이 통과해야 합니다.

### 4-2. 로그가 조용한지 (직접 확인 가능)

bamti를 띄우고 **아무것도 하지 않은 채** 3분 두었을 때 `[peek]` 줄이 하나도 늘지 않아야 합니다. Ctrl을 쓰지 않으면 어긋남이 없으므로 `ctrl split`도 나오지 않아야 합니다.

키를 몇 개 눌러 보고도 `ctrl split`이 쏟아지지 않는지 함께 보십시오.

### 4-3. 사용자 확인으로 넘길 것

**이 환경에서는 마우스와 키보드 입력을 합성할 수 없습니다. 사용자 화면에 입력을 밀어 넣으려고 하지 마십시오.**

| # | 확인 | 결과 |
| --- | --- | --- |
| 1 | 창을 드래그하는 **도중에** Ctrl을 누르고 코너로 → 전환됨 | |
| 2 | Ctrl을 **먼저** 누르고 드래그 → 여전히 전환됨 (되돌아가지 않았는지) | |
| 3 | 드래그 없이 평소처럼 Ctrl과 코너 → 여전히 전환됨 | |
| 4 | Ctrl에서 손을 뗀 뒤 코너에 올려도 **전환되지 않음** (감시가 굳지 않았는지) | |

**4번을 빠뜨리지 마십시오.** 유예를 두었기 때문에 감시가 늦게 꺼집니다. 손을 뗀 뒤 1초쯤 지나 코너에 올렸을 때 화면이 바뀌면 유예가 너무 길거나 굳음 판정이 동작하지 않는 것입니다.

## 5. 하지 말 것

- **실행부를 건드리지 마십시오.** `src/desktop_toggle.*`와 `CollectDesktopClearWindows`는 이번 범위가 아닙니다.
- 감시 주기(30밀리초), 뜸(120밀리초), 코너 폭(14 DIP), 재장전 거리(96 DIP), 예비 폴링 주기(200밀리초)를 바꾸지 마십시오. **이번에 더하는 것은 판정 하나뿐입니다.**
- 걸쇠(`peek_latched_`)의 동작을 바꾸지 마십시오.
- Raw Input을 등록하지 말고 `WH_MOUSE_LL`을 걸지 마십시오. 후보이긴 하지만 이번 범위가 아니고, 3-3절의 기록으로 필요한지부터 가립니다.
- `AttachThreadInput`으로 입력 큐를 붙여 키 상태를 읽으려 하지 마십시오.
- **훅 안에서 로그를 부르지 마십시오.** 예전에 UI 스레드를 막아 문제가 됐습니다. `ctrl split`은 타이머 쪽에서 남깁니다.
- 걷어낸 `probe` 탐침을 되살리지 마십시오.
- 레지스트리에 쓰는 확인 절차를 넣지 마십시오.

**빌드하려고 실행 중인 bamti를 종료했다면, 끝난 뒤 반드시 다시 띄워 놓으십시오.**
