# 작업 지시서 33: 독 외형을 맥 독과 같은 비율로 맞춘다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

사용자가 실제 맥 독 스크린샷과 현재 bamti 독을 나란히 비교한 결과, 모서리 곡률과 여백이 크게 다르다고 판단했습니다. 이번 작업은 독의 외형을 맥 독의 실측 비율에 맞추는 것입니다. 동작과 상호작용 로직은 건드리지 않습니다.

**추측으로 값을 정하지 마십시오.** 아래 수치는 전부 맥 독 스크린샷(4806x332, 2배 배율)을 픽셀 단위로 훑어서 얻은 실측값입니다. 이 표를 기준으로 삼으십시오.

---

## 0. 측정 근거

맥 독 스크린샷을 세로 열과 가로 행으로 스캔해서 얻은 값입니다. 2배 배율이므로 픽셀을 2로 나누면 포인트가 됩니다.

| 항목 | 실측(2x 픽셀) | 포인트 | 패널 높이 대비 |
|---|---|---|---|
| 패널 높이 | 190 | 95 | 100% |
| 패널 모서리 반지름 | 57 | 28.5 | 30.0% |
| 아이콘 크기 | 124 x 123 | 62 | 65.3% |
| 패널 왼쪽 여백 | 34 | 17 | 17.9% |
| 아이콘 위 여백 | 33 | 16.5 | 17.4% |
| 아이콘 아래 여백 | 34 | 17 | 17.9% |
| 아이콘 배치 간격(피치) | 158 | 79 | 없음 |
| 아이콘 사이 빈 공간 | 34 | 17 | 17.9% |
| 호버 라벨 알약 높이 | 52 | 26 | 없음 |
| 라벨 아래끝과 패널 위끝 사이 | 19 | 9.5 | 없음 |

여기서 읽어야 할 사실이 두 가지 있습니다.

첫째, **맥 독의 여백은 사방이 모두 같습니다.** 좌우 17pt, 위 16.5pt, 아래 17pt, 아이콘 사이 17pt가 전부 같은 값입니다. 현재 bamti는 좌우가 10dip인데 아이콘 사이는 28dip이라 균형이 깨져 있습니다.

둘째, **맥 독의 모서리는 원호에 가깝습니다.** 실측 프로파일을 반지름 28.5pt 원호와 대조하면 오차가 1~2픽셀 이내입니다. 현재 bamti가 쓰는 지수 4의 슈퍼타원은 같은 반지름에서 훨씬 각져 보입니다. 실제로 현재 독은 반지름 16dip을 지정하고도 눈에는 7dip 정도로 보이며, 이 값은 Windows 11 창 모서리(8dip)와 거의 같습니다.

## 1. 모서리 곡률을 맥과 같게 만든다

### 1.1 반지름

맥 기준은 패널 높이의 30%입니다. 독 높이가 64dip이므로 20dip입니다.

`src/corner.hpp`의 계층 상수(`kControlDip` 4, `kOverlayDip` 8, `kHeroDip` 16)는 **그대로 두십시오.** 이 값들은 동심 공식이 계층 사이를 잇도록 정해진 것이고, 팝업과 메뉴는 Windows 11 값과 일치해야 합니다.

대신 독 배경 전용 상수를 추가하십시오.

```cpp
// 독 배경 전용. 맥 독의 실측 비율(패널 높이의 30%)에서 나온 값이다.
// 계층 사다리와 무관하므로 hero 와 따로 둔다.
inline constexpr int kDockDip = 20;
```

`src/dock.cpp:2133`의 반지름 계산에서 `corner::kHeroDip`을 `corner::kDockDip`으로 바꾸십시오. `IsHero` 판정이 `tier_dip >= kHeroDip`이므로 20은 그대로 통과합니다.

### 1.2 곡선의 성격

`src/corner.hpp:26`의 `kSquircleExponent`를 `4.0f`에서 `2.4f`로 낮추십시오. 실측한 맥 독 프로파일과 맞추기 위한 값입니다.

이 상수는 Spotlight 카드에도 적용됩니다. 맥의 Spotlight 카드도 같은 계열의 곡선이므로 함께 바뀌는 편이 일관되지만, 눈에 띄는 변화이므로 검수 항목에 넣으십시오.

주석의 "4 가 애플 아이콘에 가깝고 2 면 원호와 같아진다"는 설명은 바뀐 값에 맞게 고치십시오. 실측 결과 맥의 **독 배경**은 원호에 가깝고, 지수 4에 해당하는 강한 스쿼클은 앱 아이콘 마스크 쪽 어법입니다.

### 1.3 아이콘이 모서리에 잘리지 않는지 확인

반지름 20dip, 좌우 여백 12dip, 아이콘 40dip 세로 중앙 배치일 때 첫 아이콘의 좌상단 꼭짓점은 (12, 12)이고 모서리 중심은 (20, 20)입니다. 두 점의 거리가 11.3dip으로 반지름 20dip 안쪽이므로 잘리지 않습니다. 계산은 이미 끝났지만, 실제 렌더에서 한 번 눈으로 확인하십시오.

## 2. 호버 강조 박스를 없애고 맥과 같은 라벨을 띄운다

### 2.1 없앨 것

`src/dock.cpp:2205-2214`의 호버 배경 채우기를 제거하십시오.

```cpp
if (!dragging_ && hover_ == static_cast<int>(slot_i) && hover_fill) {
  ... FillRoundedRectangle(bg, hover_fill.Get());
}
```

`hover_fill` 브러시 생성(`dock.cpp:2147`)과 `kHoverInsetDip` 상수(`dock.cpp:45`)도 다른 곳에서 쓰이지 않으면 함께 지우십시오. `hover_` 변수 자체는 라벨을 띄우는 데 계속 필요하므로 **남겨 두십시오.**

기존 Win32 툴팁도 제거 대상입니다. 다음이 전부 사라져야 합니다.

- `Dock::CreateTooltip()`(dock.cpp:1267)과 그 호출부(dock.cpp:1230)
- `tooltip_`, `tooltip_text_` 멤버(dock.hpp)
- `TTN_GETDISPINFOW` 처리(dock.cpp:1631 부근)
- `Layout()`의 `TTM_NEWTOOLRECTW` 갱신(dock.cpp:2072-2078)

### 2.2 대신 넣을 것

호버한 아이콘 위에 알약 모양 라벨을 띄웁니다. 규격은 실측값을 dip으로 옮긴 것입니다.

| 항목 | 값 |
|---|---|
| 알약 높이 | 24dip |
| 모서리 | 알약(반지름은 높이의 절반) |
| 좌우 안쪽 여백 | 10dip |
| 독 창 위끝에서 라벨 아래끝까지 | 8dip |
| 가로 정렬 | 호버한 아이콘의 가로 중심 |
| 글자 | 기존 팝업 텍스트와 같은 글꼴, `display_name` |

### 2.3 구현 방식

**독 창을 키워서 그 안에 그리지 마십시오.** 창 높이를 바꾸면 `Layout`, `HitTest`, 슬롯 좌표, 드래그 애니메이션, 핫존이 전부 영향을 받습니다. 지금 안정적으로 도는 경로를 흔들 이유가 없습니다.

대신 라벨 전용 레이어드 창을 새로 만드십시오. 새 파일 `src/dock_label.cpp`, `src/dock_label.hpp`로 분리하는 편이 기존 파일 구성 관례에 맞습니다.

- 창 클래스 이름은 `bamti.DockLabel`로 하십시오.
- 스타일은 `WS_POPUP`, 확장 스타일은 `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`입니다.
- `PopupSurface`를 재사용하지 마십시오. 캡처와 해제 로직이 붙어 있어 라벨에는 과합니다. 다만 레이어드 창을 만들고 `ID2D1DCRenderTarget`으로 그린 뒤 `UpdateLayeredWindow`로 올리는 순서는 `PopupSurface`와 `Dock::RenderLayered`를 그대로 참고하십시오.
- 글자 폭은 `PopupTextWidth`로 재고, 그리기는 `DrawPopupText`를 쓰십시오. 두 함수 모두 `popup_surface.hpp`에 이미 있습니다.
- 알약 모양은 `corner::PillPx(height)`를 반지름으로 준 `FillRoundedRectangle`로 그리십시오. 스쿼클을 쓸 자리가 아닙니다.

색은 `src/theme.cpp`에 함수 두 개를 추가해서 가져오십시오. 기존 색 함수들과 같은 형태로 작성하십시오.

```cpp
D2D1_COLOR_F DockLabelFill(bool dark);   // dark: (0.16, 0.16, 0.16, 0.95), light: (0.96, 0.96, 0.96, 0.95)
D2D1_COLOR_F DockLabelText(bool dark);   // dark: (1.0, 1.0, 1.0, 0.92),    light: (0.0, 0.0, 0.0, 0.85)
```

테두리는 기존 `DockStrokeColor(dark)`를 1픽셀 두께로 재사용하십시오.

### 2.4 표시 규칙

- `hover_`가 유효한 인덱스로 바뀌면 즉시 표시합니다. 지연을 넣지 마십시오. 맥 독은 지연 없이 뜹니다.
- `hover_`가 -1이 되면 즉시 숨깁니다.
- `dragging_`이 참이면 표시하지 않습니다.
- 독이 숨겨지거나(`HidePill`) 전체 화면에 가려지면(`SetFullscreenOccluded`) 라벨도 함께 숨깁니다.
- 라벨이 화면 좌우 밖으로 나가면 화면 안으로 밀어 넣으십시오. 독이 화면 중앙 정렬이라 끝 아이콘에서 실제로 발생할 수 있습니다.

### 2.5 박스 대신 넣는 최소한의 호버 반응

박스를 없애면 포인터가 어느 아이콘 위에 있는지 아이콘 자체로는 알 수 없습니다. `dock.cpp:2201` 부근에서 눌림 상태일 때 아이콘을 1dip 내리는 것과 같은 어법으로, 호버한 아이콘을 1dip 올리십시오.

```cpp
if (!dragging_ && hover_ == static_cast<int>(slot_i)) {
  y -= static_cast<float>(Dip(1));
}
```

눌림 처리와 순서가 겹치므로, 눌린 상태에서는 눌림 쪽이 이기도록 하십시오.

## 3. 여백과 아이콘 크기를 맥 비율로 맞춘다

### 3.1 바꿀 상수

`src/dock.cpp:42-46`입니다. 독 높이 64dip은 유지합니다.

| 상수 | 현재 | 변경 | 근거 |
|---|---|---|---|
| `kIconDip` | 36 | **40** | 맥은 65.3%, 40/64은 62.5% |
| `kSlotDip` | 64 | **52** | 아이콘 40에 간격 12를 더한 값 |
| `kPadXDip` | 10 | **12** | 맥은 17.9%, 12/64는 18.75% |
| `kHeightDip` | 64 | 64 그대로 | 바꾸지 않는다 |
| `kGroupGapDip` | 12 | 12 그대로 | 이번 범위 밖이다 |

상하 여백은 `(kHeightDip - kIconDip) / 2 = 12`로 자동으로 맞습니다. 좌우 여백, 상하 여백, 아이콘 사이 간격이 모두 12dip이 되어 맥과 같은 균등 구조가 됩니다. 이 값들은 4의 배수여서 125%, 150%, 175% 배율에서 모두 정수로 떨어집니다.

### 3.2 예상되는 눈에 띄는 변화

아이콘이 19개일 때 독 폭이 약 1248dip에서 약 1024dip으로 18% 줄어듭니다. 좁아진 것이 아니라 맥과 같은 밀도가 된 것입니다. 사용자가 놀랄 수 있으므로 보고에 반드시 적으십시오.

### 3.3 함께 확인할 것

- `kIconDip`이 바뀌면 아이콘 비트맵의 픽셀 크기가 바뀝니다. `dock.cpp:1852`, `dock.cpp:2163`, `dock.cpp:2679`가 모두 `Dip(kIconDip)`을 쓰고, 캐시 키가 `items_[i].key + L"|" + std::to_wstring(icon_px)` 형태이므로 키는 자동으로 갈라집니다. 다만 아이콘 원본이 없는 크기로 확대되어 흐려지지 않는지 확인하십시오. 150% 배율에서 40dip은 60픽셀이고, 표준 아이콘 자산은 48과 64에 있으므로 64에서 축소되는 경로가 되어야 합니다.
- 실행 표시 점(`dock.cpp:2216-2223`)의 세로 위치가 `height - Dip(10)`입니다. 아이콘이 커지면 점과 아이콘 사이가 좁아지므로, 겹치면 값을 조정하십시오. 맥은 아이콘 아래 여백 한가운데에 점을 둡니다.
- 그룹 구분선(`dock.cpp:2229-2236`)의 세로 범위가 `Dip(18)`부터 `height - Dip(18)`까지입니다. 아이콘이 40dip이 되면 구분선이 아이콘보다 짧아지므로 어색하면 조정하십시오.

## 4. 아이콘 형태 통일이 가능한지 조사한다

이 항목은 **구현이 아니라 조사입니다.** 결론을 보고서로 내고, 구현은 사용자의 판단을 받은 뒤에 하십시오.

### 4.1 질문

맥 독은 아이콘이 전부 같은 크기의 둥근 사각형으로 보입니다. Windows에서 같은 인상을 만들 수 있는지 확인하는 것이 목표입니다.

### 4.2 이미 확인된 사실

맥이 통일되어 보이는 이유는 운영체제가 아이콘을 잘라내기 때문이 아닙니다. **앱 제작자가 처음부터 둥근 사각형 캔버스에 맞춰 자산을 만들기 때문입니다.** 맥 독 스크린샷의 Chrome 아이콘은 흰 둥근 사각형 배경 위에 원형 로고가 얹힌 형태이고, Firefox도 마찬가지입니다. macOS는 iOS와 달리 아이콘에 마스크를 강제로 씌우지 않습니다.

현재 bamti 독의 아이콘은 세 부류로 나뉩니다.

1. 사각 배경이 꽉 찬 것(카카오톡, Zed, 터미널)
2. 원형인 것(Chrome, Firefox, X, GitHub)
3. 배경 없는 투명 글리프인 것(Visual Studio, 검색, 별 모양)

여기에 둥근 사각형 마스크를 씌우면 1번만 효과가 있고, 2번은 원형 그대로 남으며, 3번은 아무 변화가 없습니다. 즉 마스크만으로는 통일되지 않습니다.

### 4.3 조사할 것

근사치를 만들려면 아이콘 뒤에 배경 타일을 깔고 아이콘을 축소해 얹는 방식(안드로이드의 적응형 아이콘과 같은 접근)이 필요합니다. 다음을 확인하고 보고하십시오.

- `icon_cache.hpp`에 이미 있는 `BitmapToBgra`, `CropPaddedJumbo`, `HasStraightAlpha`로 아이콘의 알파 커버리지를 계산할 수 있는지 확인하십시오. 커버리지가 높으면 자체 배경이 있는 아이콘이고, 낮으면 투명 글리프입니다.
- 그 구분이 실제 독 아이콘들에서 안정적으로 작동하는지 확인하십시오. 실제 아이콘 20개 정도로 커버리지 수치를 뽑아서 표로 보고하십시오.
- 타일 배경색을 무엇으로 할지 판단하십시오. 아이콘의 지배색에서 뽑는 방법과 중립 회색으로 고정하는 방법 중 어느 쪽이 나은지 근거와 함께 적으십시오.
- 원형 아이콘(2번 부류)을 어떻게 다룰지 검토하십시오. 이 부류는 축소해서 타일에 얹으면 로고가 작아져 알아보기 어려워집니다.

### 4.4 미리 밝혀 둘 판단

조사 결과와 무관하게 완전한 통일은 불가능합니다. 원본 자산이 다르기 때문입니다. 얻을 수 있는 것은 들쭉날쭉한 정도를 줄이는 수준이고, 대신 브랜드 아이콘이 원래 모습과 달라지는 대가를 치릅니다. 조사 보고에는 **이 대가를 감수할 만한지에 대한 의견을 반드시 포함하십시오.**

## 검수 항목

- [ ] Release 빌드가 `/W4` 경고 없이 통과한다. CMake 빌드도 통과한다.
- [ ] 새 파일 `dock_label.cpp`를 `bamti.vcxproj`와 CMake **양쪽에** 등록했다. 한쪽만 고치면 다른 빌드가 깨진다.
- [ ] 독 모서리가 실측 기준(높이의 30%, 원호에 가까운 곡선)으로 그려진다.
- [ ] 호버할 때 박스가 나타나지 않는다.
- [ ] 호버할 때 아이콘 위쪽에 알약 라벨이 뜨고, 아이콘 가로 중심에 맞춰 정렬된다.
- [ ] 독 양 끝 아이콘에서도 라벨이 화면 밖으로 나가지 않는다.
- [ ] 드래그하는 동안에는 라벨이 뜨지 않는다.

- [ ] 좌우 여백, 상하 여백, 아이콘 사이 간격이 모두 12dip으로 같다.
- [ ] 아이콘이 흐려지지 않는다. 150% 배율에서 확인한다.
