# 작업 지시서: 미러 반응성과 오버플로 아이콘

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

트레이 미러에 남은 두 가지를 처리합니다. 하나는 완료 조건을 지키지 못하고 있는 반응성이고, 다른 하나는 `PROBE-TRAY-OVERFLOW.md`의 측정으로 가능성이 확인된 오버플로 아이콘 미러입니다.

`FIX-TRAY-PEEK.md`와 `FIX-TRAY-OVERFLOW.md`의 항목은 전부 확인했습니다. 임시 표시는 로그에서 `peek begin ms=12000` 뒤 10초 만에 `peek end`가 찍히고 그 사이 재숨김이 끼어들지 않았습니다. 오버플로 단추 판정도 `NormalButton` 조건으로 좁혀졌습니다.

---

## 1. 항목이 늘면 반영이 느려진다

### 무엇이 확정되었는가

사용자가 Windows 설정에서 서드파티 아이콘을 알림 영역으로 내보낸 뒤 미러 항목이 4개에서 10개로 늘었고, 그 결과 폴링 주기가 4.7초가 되었습니다.

```
11:53:40  [tray] items +10 -0 now=10
11:53:40  [tray] enum_ms=47 interval_ms=4700 items=10
```

`TASK-TRAY-MIRROR.md` 6-1절이 정한 `clamp(last_enum_ms * 100, 1000, 5000)` 수식이 그대로 동작한 결과입니다. 이 수식은 CPU 예산만 보고 반응성을 보지 않았습니다. 항목이 많아질수록 느려지는 방향이라, 아이콘이 많은 사람일수록 더 나쁜 경험을 하게 됩니다.

같은 문서 0절의 완료 조건은 "트레이 앱을 종료하면 2초 안에 상단바에서 사라지고, 새로 실행하면 2초 안에 나타납니다"입니다. 지금은 최대 4.7초가 걸리므로 **이 조건을 지키지 못합니다.**

폴링 배수를 낮추는 것은 답이 아닙니다. 2초를 지키려면 배수를 40 이하로 낮춰야 하는데, 그러면 열거가 전체 CPU의 2.5%를 먹습니다. 유휴 CPU 0.2% 예산과 정면으로 충돌합니다.

### 고치는 방법

변경 통지를 폴링이 아니라 UIA 이벤트로 받고, 폴링은 안전망으로만 남깁니다.

**1-1. StructureChanged 이벤트를 구독합니다.**

`IUIAutomation::AddStructureChangedEventHandler`를 열거 루트에 `TreeScope_Subtree`로 겁니다. 캐시 요청은 넘기지 마십시오(`nullptr`). 이벤트는 신호일 뿐이고 값은 우리가 다시 읽습니다.

**핸들러 안에서는 `SetEvent(wake_event_)` 하나만 하십시오.** UIA 호출도, 잠금 획득도, 로그 기록도 하지 마십시오. 이벤트 핸들러는 UIA가 자기 스레드에서 부르며, 그 안에서 UIA를 다시 호출하면 교착합니다. 이 규칙에는 예외가 없습니다.

핸들러는 `IUIAutomationStructureChangedEventHandler`를 구현하는 COM 객체입니다. 참조 카운팅을 직접 관리하고, `Stop()`에서 `RemoveStructureChangedEventHandler`(또는 `RemoveAllEventHandlers`)를 **반드시** 부른 뒤에 객체를 놓으십시오. 해제하지 않고 파괴하면 UIA가 죽은 포인터를 부릅니다.

**1-2. 디바운스합니다.**

이벤트가 오면 곧바로 열거하지 마십시오. 태스크바 서브트리에는 작업 표시줄 버튼도 들어 있어서, 창을 열고 닫을 때마다 이벤트가 옵니다.

- 마지막 이벤트로부터 **300ms**가 지난 뒤에 한 회차를 돕니다.
- 회차 사이 최소 간격은 **1000ms**입니다. 직전 열거로부터 1초가 지나지 않았으면 남은 시간만큼 미룹니다.

이 두 값을 파일 상단 상수로 빼십시오.

**1-3. 폭주를 막습니다.**

10초 동안 이벤트를 50회 넘게 받으면 구독을 끊고 폴링만으로 되돌립니다. 로그에 한 줄 남기고, 그 뒤로는 이번 프로세스 수명 동안 다시 구독하지 않습니다. 구독이 오히려 부담이 되는 환경이 있을 수 있고, 그때 조용히 느려지는 것보다 원인이 로그에 남는 편이 낫습니다.

**1-4. 폴링은 안전망으로 낮춥니다.**

구독이 살아 있으면 주기를 **5000ms 고정**으로 둡니다. 이벤트가 주 신호이므로 안전망은 느려도 됩니다. 열거가 47ms일 때 CPU는 1% 미만입니다.

구독에 실패했거나 1-3절로 끊긴 뒤에는 기존 `clamp(last_enum_ms * 100, 1000, 5000)` 수식을 그대로 씁니다. 그 경우에는 반응성보다 CPU 예산을 지키는 쪽이 맞습니다. 구독 여부를 로그의 시작 줄에 함께 적으십시오.

### 검증

- [ ] 트레이 앱을 종료하면 **2초 안에** 상단바에서 사라집니다. 스톱워치로 다섯 번 재서 최댓값을 적으십시오.
- [ ] 트레이 앱을 새로 실행하면 2초 안에 나타납니다.
- [ ] 창을 20개 빠르게 열고 닫아도 열거 횟수가 초당 1회를 넘지 않습니다. 로그로 확인합니다.
- [ ] 미러를 켠 채 10분 유휴 상태에서 CPU 사용률이 0.2% 미만입니다.
- [ ] `Stop()` 뒤에 UIA 이벤트가 더 오지 않습니다. 미러를 100번 켜고 끈 뒤에도 크래시가 없고 핸들 수가 늘지 않습니다.
- [ ] 구독에 실패한 경우를 강제로 만든 임시 빌드에서 기존 폴링 동작으로 돌아갑니다.

## 2. 오버플로 아이콘을 미러한다

### 무엇이 확정되었는가

`PROBE-TRAY-OVERFLOW.md`의 측정으로 세 가지가 확인되었습니다.

| 질문 | 측정 결과 |
|---|---|
| 안정적으로 추적할 수 있는가 | `RuntimeId`가 3초 간격 다섯 회차 동안 동일했고 열거 순서도 같았습니다 |
| 열거 비용이 얼마나 느는가 | 아이콘 2개 기준 0~16ms. 기존 보행(156ms)에 비해 작습니다 |
| `Invoke`가 가능한가 | 닫힌 상태에서도 두 버튼 모두 `IsInvokePatternAvailable=yes`입니다 |

좌표는 전부 `(0,0,0,0)`이라 순서를 좌표로 정할 수 없지만, 열거 순서 자체가 안정적이므로 그것을 씁니다.

`TASK-TRAY-MIRROR.md` 1절 6번이 "숨겨진 아이콘은 열거할 수 없다"를 전제로 삼았는데, 그 전제는 어제 측정에 근거한 것이고 지금은 뒤집혔습니다. **이 지시서가 그 전제를 대체합니다.**

### 2-1. 열거 루트를 하나 더 본다

`FindWindowW(L"TopLevelWindowForOverflowXamlIsland", nullptr)`로 창을 찾고, 그 직계 자식 가운데 클래스가 `Windows.UI.Composition.DesktopWindowContentBridge`인 창을 두 번째 루트로 씁니다. 알림 영역 루트와 똑같이 캐시하고 똑같은 조건으로 `FindAllBuildCache`를 돌립니다.

- 이 창은 없을 수 있습니다. 없으면 조용히 건너뛰고, 다음 회차에 다시 찾습니다. 없는 것을 오류로 취급하지 마십시오.
- 이 HWND도 캐시하고, `IsWindow()`가 거짓이 되거나 `TaskbarCreated`를 받으면 버립니다. 알림 영역 루트와 같은 규칙입니다.
- **오버플로 창을 열지 마십시오.** 닫힌 채로 읽는 것이 이 경로의 전제입니다.

### 2-2. 두 루트의 결과를 합친다

- 알림 영역 항목을 먼저, 오버플로 항목을 뒤에 둡니다. 사용자가 오버플로에 넣은 것은 덜 중요하다고 표시한 것이므로 바깥쪽에 놓는 것이 맞습니다.
- 알림 영역 항목은 지금처럼 `BoundingRectangle.left` 오름차순으로 정렬합니다.
- 오버플로 항목은 **열거 순서를 그대로** 씁니다. 좌표가 전부 원점이라 정렬하면 순서가 뒤죽박죽이 됩니다. 정렬하지 마십시오.
- `order`는 합친 목록에서 0부터 다시 매깁니다. `priority = kTrayPriorityBase - order`가 그대로 동작하므로, 공간이 부족하면 오버플로 항목부터 bamti 자체 오버플로 팝업으로 접힙니다. 의도한 동작입니다.

### 2-3. visible을 루트별로 다르게 정한다

**이 절을 빠뜨리면 오버플로 아이콘이 발행은 되지만 화면에 그려지지 않습니다.**

지금 `Publish`는 `item.visible = icon.offscreen == FALSE`로 정합니다. 오버플로 항목은 `IsOffscreen=yes`이므로 전부 `visible=false`가 되고, `bar_layout`이 그리지 않습니다.

`TrayIconInfo`에 `bool from_overflow = false;`를 더하고, 다음처럼 나눕니다.

```cpp
// 알림 영역 항목: explorer가 감춘 것이면 우리도 감춘다.
// 오버플로 항목: 원래 화면 밖이므로 IsOffscreen은 판단 근거가 되지 못한다.
item.visible = icon.from_overflow ? true : (icon.offscreen == FALSE);
```

### 2-4. 설정

`WidgetSettings`에 `tray_overflow_icons`를 더하고 **기본값은 켜짐**입니다.

기본값을 켜는 이유는, bamti가 태스크바를 숨기고 나면 사용자가 오버플로에 접근할 다른 경로가 없기 때문입니다. 접근할 수 없는 것보다 상단바 바깥쪽에 표시되는 편이 낫습니다. 순서상 가장 바깥에 놓이고 공간이 부족하면 먼저 접히므로, 켜져 있어도 방해가 되지 않습니다.

상단바 빈 곳 우클릭 메뉴에 "숨긴 아이콘도 표시" 항목을 더합니다. `tray_system_icons` 옆에 둡니다.

### 2-5. 클릭

좌클릭 경로는 지금 구현을 그대로 씁니다. `Invoke` 호출 시점에 `FindAll`을 다시 돌려 `key`로 찾는 방식인데, 두 루트를 다 뒤지도록 넓히기만 하면 됩니다.

**닫힌 오버플로 아이콘의 `Invoke`가 실제로 동작하는지는 아무도 확인하지 않았습니다.** 측정은 패턴 가용 여부만 조회했고 호출하지 않았습니다. 구현한 뒤 반드시 눌러 보고, 동작하지 않으면 다음을 로그에 남긴 뒤 보고하십시오.

- `Invoke`의 `HRESULT`.
- `DoDefaultAction` 폴백의 `HRESULT`.
- 눌렀을 때 앱이 반응했는지 여부.

동작하지 않는다면 오버플로 항목은 클릭할 수 없는 표시 전용이 됩니다. 그 경우 툴팁 끝에 그 사실을 덧붙이고 우클릭 메뉴의 "알림 영역 잠시 표시"로 안내하십시오. **동작하지 않는데 동작하는 것처럼 두지 마십시오.**

### 검증

- [ ] 오버플로에만 있는 아이콘이 상단바에 나타납니다.
- [ ] 알림 영역 아이콘이 먼저, 오버플로 아이콘이 뒤에 놓입니다.
- [ ] 오버플로 아이콘의 순서가 회차마다 흔들리지 않습니다.
- [ ] 오버플로 아이콘을 좌클릭했을 때의 결과를 위에 적은 세 가지로 기록했습니다.
- [ ] Windows 설정에서 아이콘을 알림 영역으로 옮기면, 상단바에서도 앞쪽으로 이동하고 중복되지 않습니다.
- [ ] `tray_overflow_icons`를 끄면 오버플로 항목만 사라지고 알림 영역 항목은 그대로입니다.
- [ ] 오버플로 창이 없는 상태(숨긴 아이콘이 하나도 없을 때)에서 오류 없이 동작합니다.
- [ ] 항목이 20개일 때 열거 시간이 100ms를 넘지 않습니다.

## 3. 함께 고칠 것

`TASK-TRAY-MIRROR.md`와 `ARCHITECTURE.md`와 `docs/STATUS-PROTOCOL.md`에 "오버플로 아이콘은 미러하지 않는다"와 "Windows 설정에서 항상 표시하도록 바꾸면 미러된다"는 문장이 들어가 있습니다. 이번 변경으로 사실이 아니게 되므로 세 곳을 모두 고치십시오.

`ShowTrayIconMenu`의 회색 안내 문구도 같습니다. "숨긴 아이콘은 Windows 설정에서 항상 표시해야 미러됩니다"를 지우고, 2-5절 확인 결과에 맞는 문구로 바꾸십시오.

`TASK-TRAY-MIRROR.md` 1절 6번은 지우지 말고, 어제 측정에 근거한 전제였으며 `PROBE-TRAY-OVERFLOW.md`가 뒤집었다는 한 줄을 덧붙이십시오. 판단이 바뀐 경위가 남아 있어야 다음에 같은 자리를 다시 파지 않습니다.

## 4. 하지 말아야 할 것

- 이벤트 핸들러 안에서 UIA를 호출하지 마십시오.
- 오버플로 창을 열지 마십시오.
- 오버플로 항목을 좌표로 정렬하지 마십시오.
- 폴링 배수를 낮춰서 반응성을 맞추려 하지 마십시오. CPU 예산과 충돌합니다.
- 캡처 경로를 다시 시도하지 마십시오. 이번 범위가 아닙니다.
