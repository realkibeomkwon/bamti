# 작업 지시서 11: 독 상호작용 복구와 코드 정리

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

안정성은 확보되었습니다. 사용자가 직접 확인한 결과, 우클릭 메뉴가 즉시 나타나고 여러 번 반복해도 멈추지 않습니다. **지금까지의 수정과 계측을 하나도 되돌리지 마십시오.**

이번 작업은 네 가지입니다. 1번부터 3번은 사용자가 보고한 기능 결함이고, 4번은 조사입니다.

## 1. 드래그로 독 아이콘 순서를 바꿀 수 없다

### 1.1 보고된 증상

> 원래는 클릭한 채로 드래그해서 독 아이콘 위치를 옮길 수 있었는데 그게 안 됩니다.

### 1.2 코드에 존재하는 경로

기능 자체는 남아 있습니다. 다음 경로가 모두 구현되어 있습니다.

```
WM_LBUTTONDOWN (dock.cpp:1209)  →  pressed_ = HitTest(pt), SetCapture(hwnd_)
WM_MOUSEMOVE   (dock.cpp:1192)  →  BeginDragIfNeeded(pt) → UpdateDrag(pt)
WM_LBUTTONUP   (dock.cpp:1225)  →  EndDrag(true)
```

`BeginDragIfNeeded`(dock.cpp:1982), `UpdateDrag`(dock.cpp:2003), `EndDrag`(dock.cpp:2016), `DisplayOrder`(dock.cpp:1960)가 전부 살아 있습니다.

**그러므로 이것은 기능이 없어서 생긴 문제가 아니라, 어딘가에서 조건이 끊겨서 생긴 문제입니다.**

### 1.3 원인을 추측하지 마십시오

지금 코드만 읽고 원인을 단정할 수 없습니다. 끊길 수 있는 지점이 여럿입니다.

- `BeginDragIfNeeded`는 `items_[pressed_].pinned`가 거짓이면 즉시 반환합니다(dock.cpp:1986). 핀 매칭이 실패하면 고정된 앱조차 `pinned=0`이 되므로 드래그가 시작되지 않습니다. 이전 지시서에서 확인한 `pin miss`가 여기에 이어질 수 있습니다.
- `WM_CAPTURECHANGED`(dock.cpp:1254)는 드래그 중이 아니면 `pressed_`를 `-1`로 되돌립니다. 버튼을 누른 직후 캡처를 빼앗기면 드래그가 시작되기 전에 상태가 날아갑니다.
- 슬롭 임계값 `kDragSlopDip = 6`(dock.cpp:41)을 넘기 전에 `pressed_`가 초기화되면 역시 시작되지 않습니다.
- `WM_MOUSEMOVE` 자체가 도달하지 않을 수도 있습니다.

**어느 것인지 확정한 뒤에 고치십시오.**

### 1.4 먼저 계측한다 (필수, 선행)

다음 네 줄을 남기십시오. 로그는 왼쪽 버튼을 누른 시점부터 뗄 때까지가 한 묶음이며, **한 번의 클릭당 최대 8줄**로 제한하십시오.

```cpp
Log(L"dock", L"drag down index=%d pinned=%d pins=%zu", pressed_, ..., pins_.size());
Log(L"dock", L"drag move dx=%d dy=%d slop=%d pressed=%d dragging=%d", ...);
Log(L"dock", L"drag skip reason=%s", reason);   // BeginDragIfNeeded 가 조기 반환할 때
Log(L"dock", L"drag capture lost to=%p dragging=%d", (HWND)lparam, dragging_ ? 1 : 0);
```

`reason`은 `not-pinned`, `already-dragging`, `no-press`, `index-out-of-range`, `below-slop` 중 하나로 적으십시오.

`drag move`는 매 이동마다 남기면 넘치므로, **한 번의 누름당 처음 3회만** 남기십시오.

### 1.5 그 다음에 고친다 (필수)

계측으로 확정된 지점을 고치십시오. 다음 원칙을 지키십시오.

- **고정되지 않은 항목도 드래그로 옮길 수 있어야 하는지는 별개 문제입니다.** 현재 설계는 고정된 항목끼리만 재정렬합니다. 그 설계는 유지하되, 고정된 항목이 `pinned=0`으로 잘못 판정되고 있다면 그것이 결함입니다.
- 핀 매칭이 원인으로 드러나면, 앞선 지시서에서 좁혀 둔 `SameDockPin` 이후의 건너뛰기 조건을 확인하십시오. `[dock] pin cmp` 줄이 이미 그 값을 남기고 있습니다.
- 원인이 캡처 손실이면, 누구에게 캡처를 빼앗겼는지 `drag capture lost` 줄로 확인한 뒤에 그 원인을 제거하십시오. `WM_CAPTURECHANGED`에서 `pressed_`를 지우는 동작 자체를 없애지는 마십시오. 캡처가 없으면 드래그를 이어갈 수 없습니다.

### 1.6 드래그 중에 반투명 아이콘이 포인터를 따라가야 한다 (필수)

현재는 슬롯 순서만 바뀌고, 끌고 있는 아이콘이 시각적으로 표현되지 않습니다. `RenderLayered`(dock.cpp:1617~1645)의 그리기 루프는 아이콘을 항상 슬롯 중앙에 그립니다.

다음과 같이 바꾸십시오.

- `Dock`에 `POINT drag_cursor_{};`를 추가하고 `UpdateDrag`에서 갱신합니다.
- `dragging_`이고 `drag_index_`에 해당하는 항목은 **슬롯 중앙에 온전히 그리지 않습니다.** 대신 그 자리에 알파 0.25로 흐리게 그려 원래 자리를 남기십시오.
- 끌고 있는 아이콘은 그리기 루프가 끝난 뒤에 **마지막으로** 그립니다. 가로 위치는 `drag_cursor_.x`를 중심으로 하고, 세로는 평소보다 `Dip(3)`만큼 위로 올리며, 알파는 **0.7**로 합니다. 다른 아이콘 위에 겹쳐 보여야 하므로 그리는 순서가 중요합니다.
- 가로 위치는 독의 클라이언트 영역 안으로 제한하십시오. 아이콘이 독 밖으로 잘려 나가면 안 됩니다.

**중요한 제약이 있습니다.** 독 창은 `WS_EX_NOACTIVATE` 배경 창이므로, 캡처를 잡아도 커서가 창의 보이는 영역 안에 있을 때만 마우스 메시지를 받습니다. 따라서 고스트 아이콘이 독 밖으로 나가는 동작은 애초에 구현할 수 없습니다. **별도의 창을 새로 만들어 이 제약을 우회하려 하지 마십시오.** 재정렬은 독 안에서만 일어나므로 지금 구조로 충분합니다.

### 1.7 다시 그리는 비용을 재고 제한한다 (필수)

`UpdateDrag`(dock.cpp:2003)는 현재 **드롭 위치가 바뀔 때만** `RenderLayered()`를 부릅니다. 고스트가 포인터를 따라가려면 이동할 때마다 다시 그려야 하므로 호출 빈도가 크게 늘어납니다.

- 마지막으로 그린 시점으로부터 **16ms**가 지났을 때만 다시 그리십시오. `GetTickCount64()`를 기준으로 판정합니다.
- 드롭 위치가 바뀌는 순간은 이 제한과 무관하게 즉시 그리십시오.
- 드래그를 한 번 마칠 때, 그 사이의 `RenderLayered` 호출 횟수와 평균 소요 시간을 한 줄로 남기십시오.

```cpp
Log(L"perf", L"drag render n=%u avg=%.1fms max=%ums", ...);
```

이 줄로 고스트 렌더링이 감당할 만한 비용인지 판단합니다. 평균이 5ms를 넘으면 보고하십시오.

## 2. 열린 창이 없는 앱의 메뉴에 "새 창"이 없다

### 2.1 보고된 증상

> 열린 창이 없는 앱의 아이콘을 우클릭하면 메뉴에 고정 해제만 있습니다. 새 창(New Window) 버튼이 있어야 합니다.

### 2.2 현재 구조

`DockMenuContent::Reset`(dock.cpp:694)이 메뉴 항목을 만듭니다. `모두 보기`, `가리기`, `종료`는 `has_windows`가 참일 때만 추가되고(dock.cpp:740~745), 창이 없으면 `고정 해제` 또는 `독에 고정` 한 줄만 남습니다. **앱을 새로 실행하는 항목은 어느 경우에도 없습니다.**

실행 자체는 이미 가능합니다. 왼쪽 클릭 처리(dock.cpp:1246)가 `LaunchDockApp(app)`을 부르고, 그 함수(task_list.cpp:1110)는 AUMID, relaunch 명령, 실행 파일 경로를 차례로 시도합니다.

### 2.3 수정 지시 (필수)

- 명령 상수를 추가하십시오. `constexpr UINT kNewWindowCommand = 6;`을 dock.cpp:65~70 묶음에 넣습니다.
- `MenuCmdName`(dock.cpp:87)에 `case kNewWindowCommand: return L"new-window";`를 추가하십시오. 계측이 명령 이름을 남기고 있으므로 빠뜨리면 로그에 `none`이 찍힙니다.
- `Reset`에서 **메뉴의 맨 위**에 `새 창` 항목을 넣으십시오. 창 목록보다 위입니다.
  - 조건은 `LaunchDockApp`이 성공할 여지가 있는 경우입니다. 즉 `app.aumid`, `app.relaunch_command`, `app.exe_path` 중 **하나라도 비어 있지 않을 때** 넣습니다.
  - 자기 자신(`IsSelfExecutable(app.exe_path)`)에는 넣지 마십시오.
  - **창이 열려 있을 때도 넣으십시오.** macOS의 New Window와 같은 동작입니다. 사용자가 요구한 상황은 창이 없을 때이지만, 창이 있을 때 이 항목을 막을 이유가 없습니다.
  - 창 목록이 뒤따르면 그 사이에 구분선을 넣으십시오. 기존 `add_sep()` 람다를 쓰십시오.
- `ApplyMenuCommand`(dock.cpp:1859)에 분기를 추가하십시오.

  ```cpp
  } else if (cmd == kNewWindowCommand) {
    if (!LaunchDockApp(app)) {
      Log(L"dock", L"new-window failed name=%s", app.display_name.c_str());
    }
  }
  ```

- 실행에 성공했다고 해서 `pending_rebuild_`를 억지로 세우지 마십시오. 새 창이 생기면 기존 창 감시 훅이 재구성을 일으킵니다.

## 3. 아이콘에 마우스를 올려도 아무 반응이 없다

### 3.1 보고된 증상

> 앱 아이콘에 마우스 포인터 호버 시 이펙트가 없기 때문에 유저가 직관적으로 어떤 앱이 선택될 것인지 알 수가 없습니다.

### 3.2 현재 구조

독 항목에는 호버 상태가 **존재하지 않습니다.** `dock.hpp`의 멤버 어디에도 없습니다. 눌린 상태(`pressed_`)만 있고, 그것도 아이콘을 1dip 아래로 내리는 것이 전부입니다(dock.cpp:1623).

툴팁은 독 전체를 하나의 도구 영역으로 잡고 `TTN_GETDISPINFO`(dock.cpp:1291)에서 커서 위치로 항목을 고릅니다. 즉 **호버 인덱스를 따로 들고 있지 않습니다.**

팝업 메뉴 쪽에는 이미 호버 색이 있습니다. `MenuItemHoverFill(dark, false)`(dock.cpp:787)입니다.

### 3.3 수정 지시 (필수)

- `Dock`에 `int hover_ = -1;`을 추가하십시오.
- `WM_MOUSEMOVE`(dock.cpp:1192)에서 `HitTest(pt)` 결과로 갱신하십시오. **값이 실제로 바뀔 때만** `RenderLayered()`를 부르십시오. 커서가 움직일 때마다 다시 그리면 안 됩니다.
- `WM_MOUSELEAVE`(dock.cpp:1204)와 `HidePill()`에서 `-1`로 되돌리십시오.
- `dragging_`이 참인 동안에는 호버를 그리지 마십시오. 고스트 아이콘과 겹쳐 어지러워집니다.
- 그리기는 `RenderLayered`의 아이콘 루프 안에서, **아이콘보다 먼저** 배경으로 넣으십시오.
  - 모양은 슬롯을 세로로 조금 줄인 둥근 사각형입니다. 반지름은 `Dip(8)`이고, 슬롯의 위아래를 각각 `Dip(4)`만큼 안쪽으로 줄이십시오.
  - 색은 `MenuItemHoverFill(dark_, false)`를 그대로 쓰십시오. 메뉴와 같은 색이어야 일관됩니다.
- 크기를 키우는 확대 효과(macOS의 magnification)는 **넣지 마십시오.** 이번 범위가 아닙니다.

### 3.4 비용 확인 (필수)

호버가 바뀔 때마다 `UpdateLayeredWindow`가 일어납니다. 독 위에서 커서를 좌우로 10초간 빠르게 움직이며 CPU를 재서 보고하십시오.

```powershell
$p = Get-Process bamti; $c=$p.TotalProcessorTime.TotalSeconds; Start-Sleep 10; $p.Refresh()
"{0:N2} cores" -f (($p.TotalProcessorTime.TotalSeconds-$c)/10)
```

0.1 코어를 넘으면 보고하십시오. 그 경우에는 호버 렌더링에도 16ms 제한을 넣습니다.

## 4. 코드 정리 (조사가 먼저입니다)

### 4.1 사용자의 지적

> 지금까지 근본적인 원인을 해결하지 못하고 땜질식으로 수정을 계속 반복해왔기 때문에 코드가 불필요하고 최적화되지 못한 부분이 많을 것이므로 코드 리팩토링, 최적화가 필요하다고 생각합니다.

타당한 지적입니다. 다만 **지금 코드를 넓게 뜯어고치면 방금 확보한 안정성을 잃습니다.** 그러므로 이번에는 고치지 않고 목록을 만듭니다.

### 4.2 계측 장치는 남깁니다

다음은 땜질이 아니라 진단 장비입니다. **제거 대상으로 올리지 마십시오.**

- 감시 스레드와 `watchdog.log` (`src/watchdog.cpp`)
- `[perf] msg flood` 메시지 처리량 집계 (`src/host.cpp`)
- 게시 메시지 계수기와 `storm` 경고
- `[popup] alive tick` 과 `dismiss reason`
- `[dock] pin cmp`, `pin miss`

조용할 때는 비용이 들지 않고, 이번 멈춤의 원인을 찾아낸 것이 바로 이 장치들입니다. `pin cmp`만은 핀 문제가 해결된 뒤에 제거 후보가 됩니다.

### 4.3 조사해서 보고할 것 (필수)

`REFACTOR-NOTES.md`를 새로 만들고, 아래 각 항목에 대해 **근거와 함께** 적으십시오. 근거 없이 "불필요해 보임"이라고 적지 마십시오.

1. **`WM_PAINT`와 `Paint()`가 실제로 불리는가.** 독 창은 `UpdateLayeredWindow`로 그립니다. `HandleMessage`의 `case WM_PAINT`(dock.cpp:1120)에 로그를 넣고 30분간 정상적으로 사용한 뒤, 한 번이라도 불렸는지 보고하십시오.
2. **`HandleHot`과 `HandleMessage`의 중복.** `WM_MOUSELEAVE` 처리가 양쪽에 있습니다(dock.cpp:1088, 1204). 합칠 수 있는지, 합치면 무엇이 깨지는지 적으십시오.
3. **`PollPointer` 타이머가 아직 필요한가.** `kPollTimerId`(dock.cpp:1757)는 `kIdlePollMs` 주기로 돕니다. 지금은 팝업의 `Tick()`과 마우스 이벤트가 대부분을 처리합니다. 이 타이머를 껐을 때 무엇이 동작하지 않는지 **실제로 꺼 보고** 적으십시오. 결론이 나기 전에 커밋하지는 마십시오.
4. **`icon_cache_`의 생명 주기.** 키가 무엇이고, 언제 비워지며, `HBITMAP`이 새는 지점이 있는지 적으십시오.
5. **`CollectDockApps` 한 번의 소요 시간 분해.** 창 열거, 프로퍼티 읽기, 아이콘 추출이 각각 몇 ms인지 재서 적으십시오. 이 값이 없으면 최적화 대상을 고를 수 없습니다.
6. **컴파일러가 확인해 주는 죽은 코드.** 호출되지 않는 함수와 쓰이지 않는 멤버를 열거하십시오. 이것만은 이번에 제거해도 됩니다.

### 4.4 이번에 해도 되는 것 (선택)

6번의 죽은 코드 제거만 별도 커밋으로 하십시오. **그 외에는 이번 지시서에서 고치지 마십시오.** 보고를 받은 뒤에 별도 지시서로 다룹니다.

## 6. 검증

**드래그**
- [ ] 고정된 아이콘을 눌러 좌우로 끌면 순서가 바뀐다.
- [ ] 끄는 동안 반투명 아이콘이 포인터를 따라온다.
- [ ] 원래 자리에 흐린 아이콘이 남는다.
- [ ] 버튼을 떼면 새 순서가 저장되고, 프로그램을 재시작해도 유지된다.
- [ ] 드래그하지 않고 그냥 클릭하면 앱이 활성화된다. 이 동작이 깨지지 않았다.
- [ ] `[perf] drag render` 줄의 평균 소요 시간을 보고한다.
- [ ] 드래그가 되지 않았다면 `[dock] drag skip reason=` 줄 전체를 보고한다.

**새 창**
- [ ] 열린 창이 없는 고정 앱을 우클릭하면 `새 창`과 `고정 해제`가 보인다.
- [ ] `새 창`을 누르면 앱이 실행된다.
- [ ] 창이 열려 있는 앱에도 `새 창`이 맨 위에 보이고, 그 아래에 구분선과 창 목록이 온다.
- [ ] `[dock] menu cmd=6 new-window` 줄이 남는다.

**호버**
- [ ] 아이콘 위에 커서를 올리면 배경이 밝아진다.
- [ ] 아이콘 사이를 옮기면 강조도 함께 옮겨진다.
- [ ] 독 밖으로 나가면 강조가 사라진다.
- [ ] 드래그 중에는 호버가 그려지지 않는다.
- [ ] 3-4의 CPU 측정값을 보고한다.

**회귀**
- [ ] 우클릭 메뉴가 즉시 열리고 바깥 클릭으로 닫힌다. 스무 번 반복해도 멈추지 않는다.
- [ ] 독이 표시되고 유지되고 숨겨진다.
- [ ] `watchdog.log`에 `alive stage=idle ping=ok`만 쌓인다.
- [ ] `[perf] msg flood` 줄이 남지 않는다.
- [ ] 유휴 60초 누적 CPU가 1초 미만이다.
- [ ] Release 빌드가 `/W4` 경고 없이 통과한다.
