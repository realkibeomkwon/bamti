# 작업 지시서: 창을 트레이로 감추는 앱이 독에서도 트레이에서도 사라지는 문제를 고친다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

건드리는 파일은 `src/task_list.cpp`, `src/dock.cpp`, `src/tray_intercept.cpp` 세 개입니다. **1단계와 2단계는 독립이므로 순서대로 하나씩 끝내고 각각 검증하십시오.**

---

## 1. 증상

카카오톡은 창을 모두 닫으면 프로세스가 남은 채 트레이로 들어가도록 만들어져 있습니다. 그런데 **카카오톡 창이 열린 상태에서 bamti 를 새로 실행한 뒤 카카오톡 창을 모두 닫으면**, 독은 그 앱을 창 없음으로 표시하고 상단바 트레이에도 카카오톡이 없습니다. 사용자가 그 앱에 닿을 방법이 화면에서 사라집니다.

같은 방식으로 동작하는 앱이 여럿이므로 카카오톡 하나의 문제로 다루면 안 됩니다.

---

## 2. 무엇이 원인인가 (로그로 확정)

### 2-1. 트레이: 재등록 응답이 실행마다 다르다

`~/.bamti/bamti.log` 의 `[tray] intercept item` 과 `[tray] intercept roster` 줄을 시각 순으로 늘어놓으면 다음과 같습니다.

| bamti 시작 시각 | 가로채기가 잡은 항목 |
| --- | --- |
| 09:25:05 | Everything, 오피스키퍼, Bluetooth 장치, (툴팁 없음), **KakaoTalk**, Tailscale — 여섯 개 |
| 09:26:13 | 오피스키퍼, Everything, Bluetooth 장치, (툴팁 없음) — **네 개. KakaoTalk 과 Tailscale 이 없다** |
| 09:29:30 | `intercept item tip="" exe=KakaoTalk.exe hwnd=0x408FA uid=222` — 시작하고 **3분 17초 뒤에** 툴팁도 없이 뒤늦게 들어왔다 |

**44초 간격으로 두 번 시작했는데 결과가 달랐습니다.** 09:26:13 회차에서 카카오톡은 우리가 보낸 `TaskbarCreated` 브로드캐스트에 응답하지 않았습니다.

`docs/research/RESEARCH-TRAY-REREGISTER.md` 가 이미 기록한 대로, 재등록은 앱이 스스로 구현해야 하는 규약이고 우리가 강제할 수 없습니다. 여기서 확인된 것은 그보다 나쁜 상황입니다. **같은 앱이 응답할 때도 있고 하지 않을 때도 있습니다.** 브로드캐스트를 더 보내는 것만으로는 해결되지 않습니다.

응답하지 않은 아이콘은 사라진 것이 아니라 **explorer 안에 그대로 남아 있습니다.** 다만 bamti 가 작업 표시줄을 자동 숨김으로 밀어 두었기 때문에 사용자가 볼 수 없을 뿐입니다.

### 2-2. 독: 창이 없으면 실행 중이 아니라고 판정한다

같은 로그의 독 쪽 줄입니다.

```
10:07:29.199 [dock] click index=16 running=1 hwnd=0000000000020910 name=KakaoTalk
10:07:53.755 [dock] click index=16 running=0 hwnd=0000000000000000 name=KakaoTalk
```

카카오톡 프로세스는 계속 살아 있었는데도 `running=0` 입니다. `CollectDockApps`(`src/task_list.cpp` 1325행)는 최상위 창을 열거해서 앱을 모으므로, 창이 하나도 없는 앱은 고정 항목으로만 남고 `DockApp::running` 이 기본값 false 로 남습니다(1578행부터의 마지막 `else` 분기).

그 결과 표시등이 꺼지고, 오른쪽 단추 메뉴에 창 목록이 뜨지 않습니다. 왼쪽 단추로 누르면 `LaunchDockApp` 이 불려 기존 인스턴스가 창을 다시 여는 것은 **지금도 동작합니다.** 고칠 것은 상태 표시이지 실행 경로가 아닙니다.

---

## 3. 1단계: 독이 창 없는 실행 중 앱을 알아보게 한다

이쪽을 먼저 하십시오. 변경이 작고, 이것만으로도 사용자가 앱에 닿을 길이 생깁니다.

### 3-1. 프로세스가 살아 있는지 확인하는 함수를 더한다

`src/task_list.cpp` 의 익명 이름공간에 다음 뜻의 함수를 더하십시오.

```cpp
// 주어진 실행 파일 경로로 도는 프로세스가 있는지 본다. 창이 없어도 참을 돌려준다.
bool ExeHasLiveProcess(const std::wstring& exe_path);
```

구현할 때 지켜야 할 것이 세 가지 있습니다.

1. `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)` 로 한 번만 훑고, 그 안에서 실행 파일 이름만 비교하십시오. 프로세스마다 핸들을 열어 전체 경로를 얻으면 느립니다. 이름이 같은 프로세스가 여럿일 때에만 `QueryFullProcessImageNameW` 로 좁히십시오.
2. **결과를 캐시하십시오.** 이 함수는 독을 다시 모을 때마다 불리므로, 스냅숏을 1초에 한 번보다 자주 뜨지 않게 하십시오. 캐시는 실행 파일 이름을 열쇠로 하는 집합 하나면 충분합니다.
3. 경로 비교는 이 파일에 이미 있는 `CanonicalPath` 와 `SameDockPin` 의 방식을 그대로 따르십시오. 새 비교 규칙을 만들지 마십시오.

### 3-2. 고정 항목에 이 판정을 붙인다

`CollectDockApps` 의 1578행부터, 창을 찾지 못한 고정 앱을 만드는 마지막 `else` 분기에서 `app.exe_path` 를 채운 뒤에 다음을 더하십시오.

```cpp
      // 창을 트레이로 감추는 앱은 창이 없어도 프로세스가 살아 있다.
      if (!app.exe_path.empty() && ExeHasLiveProcess(app.exe_path)) {
        app.running = true;
      }
```

`app.hwnd` 는 `nullptr` 로 두십시오. 창이 실제로 없으므로 채울 것이 없습니다.

AUMID 로 고정한 항목(1560행부터)에도 `app.exe_path` 가 채워지는 경로가 있으므로 같은 처리를 더하십시오. 경로를 얻지 못한 경우에는 건너뛰십시오.

### 3-3. 클릭과 메뉴가 어긋나지 않게 한다

`src/dock.cpp` 1498행의 클릭 분기는 `app.running && app.hwnd != nullptr` 를 보므로, `running` 만 참이고 `hwnd` 가 없으면 지금처럼 `LaunchDockApp` 으로 갑니다. **이 조건을 바꾸지 마십시오.** 창이 없는 앱을 다시 실행하는 것이 곧 창을 되살리는 방법입니다.

오른쪽 단추 메뉴(`DockMenuContent::Reset`)에서는 창 목록이 비어 있을 때에도 실행 중인 앱에 맞는 항목이 뜨는지 확인하십시오. 창 목록만 보고 메뉴가 비어 버리면 2350행의 `menu empty` 로그가 남고 메뉴가 열리지 않습니다. 그런 경우라면 실행 중이지만 창이 없는 상태에 맞는 항목을 보이게 하십시오.

### 3-4. 1단계 검증

**로그가 아니라 화면과 프로세스 상태로 판정하십시오.**

1. 카카오톡을 실행하고 창을 연 채 bamti 를 재시작한다.
2. 카카오톡 창을 모두 닫는다. 프로세스가 남아 있는 것을 `Get-Process KakaoTalk` 으로 확인한다.
3. 독의 카카오톡 항목에 **실행 중 표시등이 켜져 있어야 합니다.** 이것이 성공 판정입니다.
4. 로그에 `[dock] click ... running=1 hwnd=0000000000000000 name=KakaoTalk` 이 남아야 합니다. `running=0` 이면 실패입니다.
5. 그 항목을 눌러 창이 다시 열리는지 확인한다.
6. 카카오톡을 완전히 종료한 뒤 표시등이 꺼지는지 확인한다. **꺼지지 않으면 캐시가 오래된 값을 붙들고 있는 것이므로 실패입니다.**

독을 다시 모으는 데 걸리는 시간이 늘지 않았는지도 확인하십시오. 로그의 `[dock]` 수집 시간 관련 줄에서 이전 값과 비교하고, 눈에 띄게 늘었다면 3-1 의 캐시를 다시 보십시오.

## 4. 2단계: 가로채기가 놓친 트레이 아이콘을 UIA 열거로 메운다

1단계를 끝내고 검증한 뒤에 시작하십시오.

### 4-1. 먼저 UIA 가 그 아이콘을 볼 수 있는지 확인한다

**이 확인을 건너뛰고 구현에 들어가지 마십시오.** 작업 표시줄을 자동 숨김으로 밀어 둔 상태에서 UIA 열거가 성립하는지가 전제입니다. `docs/research/PROBE-TRAY-PARKED.md` 에 관련 기록이 있으니 먼저 읽으십시오.

`src/tray_mirror.cpp` 986행 부근에 이미 `LogDiagRosters` 가 있어 두 백엔드를 동시에 열거합니다. 이것을 시작 직후에 한 번 부르도록 임시로 손보고, 2-1 과 같은 상황(가로채기가 카카오톡을 놓친 회차)을 만들어 다음을 확인하십시오.

- `uia roster` 에 카카오톡이 들어 있는가.
- 들어 있다면 그 항목의 `key`, `automation_id`, `class_name`, 툴팁이 무엇인가.

**UIA 로스터에도 없다면 이 방향은 성립하지 않습니다.** 구현을 멈추고 측정 결과를 보고하십시오.

### 4-2. 보충 규칙

UIA 로스터에는 있는데 가로채기 로스터에는 없는 항목만 보충 대상입니다. 다음 규칙을 지키십시오.

1. **가로채기가 가진 항목을 UIA 값으로 덮지 마십시오.** 가로채기 쪽이 항상 우선입니다.
2. 같은 항목인지는 툴팁과 소유 프로세스의 실행 파일 이름으로 봅니다. **툴팁이 비어 있으면 같은 항목이라고 단정하지 말고 보충하지 않는 쪽을 고르십시오.** 2-1 의 09:29:30 줄처럼 툴팁 없이 들어오는 경우가 실제로 있습니다. 중복으로 두 개가 뜨는 것이 하나가 사라지는 것보다 나쁩니다.
3. 보충한 항목의 클릭은 UIA 의 `Invoke` 경로로 처리하십시오. 그 항목에는 가로채기가 아는 콜백 메시지가 없으므로 콜백을 보내면 아무 일도 일어나지 않습니다.
4. 보충한 항목에는 출처를 남겨 로그에서 구별할 수 있게 하십시오. `[tray] fill key=... exe=... tip=...` 정도면 됩니다.
5. 보충 열거는 **시작 직후와 재브로드캐스트 직후에만** 수행하십시오. 주기적으로 UIA 를 훑으면 열거 비용 때문에 `slow_streak_` 가 쌓여 미러가 스스로 멈춥니다(`kSlowStreakStop`).

### 4-3. 재브로드캐스트를 조금 늘린다

`src/tray_intercept.cpp` 의 `kRebroadcastMax`(50행)는 3, `kRebroadcastWindowMs` 는 60000 입니다. 2-1 에서 본 것처럼 응답이 늦는 앱이 있으므로, 시작 직후에 한해 시간 간격을 벌려 몇 번 더 보내십시오. 0초, 2초, 6초, 15초 네 번이면 충분합니다.

**상시로 보내지 마십시오.** `TaskbarCreated` 는 앱에게 아이콘 전체를 다시 만들라는 뜻이므로, 자주 보내면 앱이 깜빡이거나 무시하기 시작합니다.

### 4-4. 2단계 검증

1. 카카오톡과 Tailscale 을 띄워 둔 채 bamti 를 **열 번 재시작**하십시오.
2. 매 회차마다 상단바에 카카오톡 아이콘이 보이는지 확인하십시오. **판정 기준은 로스터 로그의 개수가 아니라 상단바에 실제로 보이는 아이콘입니다.** 로그의 개수가 맞는데 화면에 없다면 `tray_hidden_keys` 에 걸린 것이므로 그 사실을 따로 보고하십시오.
3. 열 번 모두 보여야 합니다. 한 번이라도 빠지면 실패입니다.
4. 보충으로 들어온 아이콘을 눌러 앱의 메뉴가 뜨는지 확인하십시오.
5. 아이콘이 두 개로 겹쳐 보이는 회차가 있는지 확인하십시오. 있으면 4-2 의 2번 규칙을 다시 보십시오.
6. `[tray] auto-stop` 로그가 남지 않아야 합니다. 남았다면 열거가 느려진 것입니다.

## 5. 빌드

Release 빌드가 경고 없이 통과해야 합니다. **CMake 로 빌드하십시오.** `bamti.vcxproj` 는 소스 열네 개가 빠져 있어 msbuild 로는 링크되지 않습니다.

```
cmake -S D:\repos\bamti -B <빌드 디렉터리>
cmake --build <빌드 디렉터리> --config Release
```

## 6. 건드리지 말 것

- 가로채기 백엔드가 스파이 창의 Z 순서를 지키는 처리(`kPrioTimer` 계열)를 바꾸지 마십시오. 이것이 무너지면 아이콘을 하나도 받지 못합니다.
- `TrayMirror::DoRound` 의 자동 정지 조건(`kSlowEnumMs`, `kSlowStreakStop`)을 느슨하게 풀지 마십시오. 그 조건은 UIA 열거가 셸을 느리게 만드는 것을 막습니다.
- `item.visible` 판정(`icon.from_overflow ? true : (icon.offscreen == FALSE)`)을 바꾸지 마십시오. explorer 가 감춘 아이콘을 우리가 되살리는 것은 별개의 결정입니다.
- 사용자가 숨긴 항목 목록(`tray_hidden_keys`)을 코드에서 지우거나 비우지 마십시오.
- 작업 표시줄을 다시 보이게 하는 방향으로 우회하지 마십시오. 감추는 것이 이 프로그램의 목적입니다.
- `LaunchDockApp` 과 `ActivateHwnd` 의 동작을 바꾸지 마십시오.
