# 작업 지시서 2: 팝업 메뉴가 마우스 입력을 전혀 받지 못하는 문제

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

커밋 `19153dc` 이후에도 메뉴가 조작되지 않습니다. 이 문서는 남은 원인과 수정 방법을 지정합니다.

앞선 `FIX-POPUP.md`는 **표시 지연**을 다뤘고 그 부분은 해결되었습니다. 이번 문서는 **입력 처리**를 다룹니다. 두 문제는 별개입니다.

---

## 0. 해결된 것과 남은 것

### 해결됨: 표시 지연

```
08:37:07.528 [dock] menu open index=0 name=explorer.exe running=1 windows=1 pinned=1
08:37:07.537 [popup] open rows=7 shown 15ms
```

`shown 15ms`입니다. 목표치 16ms를 만족합니다. 화면 캡처에서도 메뉴 항목(`고정 해제`, `모두 보기`, `가리기`, `종료`)이 정상으로 그려집니다. **`UpdateWindow()` 수정은 성공했으므로 되돌리지 마십시오.**

### 남음: 입력이 전혀 처리되지 않음

같은 로그에서 메뉴가 열린 뒤 **아무 줄도 추가되지 않았습니다.**

- `[popup] dismiss reason=...` 없음
- `[dock] menu cmd=...` 없음

사용자는 `모두 보기`를 클릭했습니다. 그런데 `Dismiss()`는 첫 줄에서 무조건 로그를 남기므로, **`Dismiss()`가 한 번도 호출되지 않았습니다.** 즉 클릭이 팝업의 `Handle()`에 도달하지 않았거나, 도달했어도 어떤 분기에도 걸리지 않았습니다.

메뉴는 화면에 그려진 채 조작만 되지 않는 **죽은 그림** 상태입니다.

---

## 1. 원인

`FIX-POPUP.md` 2.2절에서 확인한 `SetCapture` 제약이 예상보다 넓게 작용합니다. 문서의 서술은 다음과 같습니다.

> Only the foreground window can capture the mouse. When a background window attempts to capture the mouse, the window receives messages only for mouse events that occur when the cursor hot spot is within the visible region of the window.

`PopupSurface`는 `WS_EX_NOACTIVATE`라 포그라운드가 되지 않습니다. 지난 수정에서는 이 제약이 **팝업 바깥 클릭**에만 영향을 준다고 보고 가드 타이머 폴링으로 보완했습니다. 그런데 실제로는 **팝업 안쪽 클릭도 도달하지 않습니다.**

그 결과 현재 팝업의 입력 경로는 다음 상태입니다.

| 동작 | 처리 주체 | 현재 상태 |
|---|---|---|
| 팝업 바깥 클릭 | 가드 타이머 폴링 | 작동함 |
| 팝업 안쪽 클릭 (명령 실행) | `Handle()`의 `WM_LBUTTONUP` | **작동 안 함** |
| 항목 위 호버 강조 | `Handle()`의 `WM_MOUSEMOVE` | **작동 안 함** |
| `ESC`, `Win` 키 | 가드 타이머 폴링 | 작동함 |

메시지에 의존하는 두 가지가 모두 죽었습니다. 반면 폴링에 의존하는 것들은 살아 있습니다. **이 대비가 원인을 가리킵니다.**

## 2. 방침

메시지 경로를 고치려 하지 말고, **이미 작동이 확인된 가드 타이머 폴링으로 입력 처리를 일원화하십시오.**

가드 타이머는 이미 50ms마다 돌면서 마우스 버튼 눌림 전이를 감지하고 있고, 그 경로는 실제로 작동합니다. 여기에 안쪽 클릭과 호버만 더하면 됩니다. 새 메커니즘을 도입할 필요가 없습니다.

`FIX-POPUP.md` 3-6에 적어 둔 `WH_MOUSE_LL` 훅은 **지금 단계에서는 쓰지 마십시오.** 시스템 전역 입력 경로에 개입하는 방식이므로, 이미 있는 폴링으로 해결되는지 먼저 확인해야 합니다. 5장의 검증을 통과하지 못할 때만 다시 논의합니다.

---

## 3. 수정 지시

대상은 `src/popup_surface.cpp`의 `OnGuardTimer()`입니다.

### 3-1. 안쪽 클릭으로 항목을 실행한다 (필수)

현재 `OnGuardTimer()`의 마우스 처리는 눌림 전이만 보고, 커서가 팝업 바깥일 때만 닫습니다.

```cpp
if (mouse && !mouse_down_) {
  if (커서가 팝업 밖) Dismiss(-1, DismissReason::kOutsidePoll);
}
mouse_down_ = mouse;
```

이를 **눌림과 뗌을 모두 추적하는 형태**로 바꾸십시오. 실제 메뉴 조작은 버튼을 뗄 때 확정되어야 합니다. 누르자마자 실행하면 드래그로 항목을 바꿀 수 없고, 실수로 누른 뒤 벗어나도 실행되어 버립니다.

동작 규칙은 다음과 같습니다.

1. **눌림 전이**(`mouse && !mouse_down_`)
   - 커서가 팝업 **바깥**이면 `Dismiss(-1, kOutsidePoll)`로 닫습니다. 지금과 같습니다.
   - 커서가 팝업 **안쪽**이면 닫지 않고, "안쪽에서 눌렸다"는 사실을 기록합니다. 새 멤버 `bool press_inside_`를 `popup_surface.hpp`에 추가하십시오.
2. **뗌 전이**(`!mouse && mouse_down_`)
   - `press_inside_`가 참이고 커서가 여전히 팝업 안쪽이면, 클라이언트 좌표로 변환해 `content_->HitTest()`를 부릅니다.
     - 결과가 0 이상이면 `Dismiss(그 값, DismissReason::kInvoke)`
     - 결과가 -1이면(구분선이나 여백) 닫지 않고 그대로 둡니다.
   - `press_inside_`가 참인데 커서가 팝업 밖으로 나갔으면 아무것도 하지 않고 `press_inside_`만 해제합니다. 사용자가 실행을 취소한 것입니다.
   - 마지막에 `press_inside_ = false`로 되돌립니다.

`press_inside_`는 `Open()`에서 `false`로 초기화하십시오.

좌표 변환에는 `ScreenToClient()`를 쓰십시오. `HitTest()`가 클라이언트 좌표를 받기 때문입니다.

### 3-2. 폴링으로 호버를 갱신한다 (필수)

같은 `OnGuardTimer()` 안에서, 커서가 팝업 안쪽일 때 `HitTest()` 결과로 `hot_`을 갱신하십시오. 값이 바뀐 경우에만 `InvalidateRect` + `UpdateWindow`를 호출합니다. 커서가 바깥이면 `hot_`을 -1로 되돌립니다.

값이 바뀌지 않았는데 다시 그리면 50ms마다 불필요한 렌더가 돌게 되므로, **반드시 변화가 있을 때만** 그리십시오.

`Handle()`의 기존 `WM_MOUSEMOVE` 처리는 지우지 말고 그대로 두십시오. 메시지가 도착하는 환경에서는 그쪽이 더 부드럽고, 두 경로가 같은 결과를 내므로 충돌하지 않습니다.

### 3-3. 입력 경로를 계측한다 (필수)

이번 진단이 어려웠던 이유는 팝업이 마우스 메시지를 받는지 여부를 알 방법이 없었기 때문입니다. 다음을 남기십시오.

`Handle()`의 `WM_LBUTTONDOWN`, `WM_RBUTTONDOWN`, `WM_LBUTTONUP`, `WM_RBUTTONUP` 진입 지점에서 한 줄씩 기록합니다.

```cpp
Log(L"popup", L"msg=%s pt=%d,%d inside=%d", /* 메시지 이름 */, pt.x, pt.y, /* 클라이언트 안쪽 여부 */);
```

`WM_MOUSEMOVE`는 빈도가 높으므로 로그를 넣지 마십시오. 대신 `Open()` 이후 `WM_MOUSEMOVE`를 처음 받았을 때만 한 번 기록하십시오. 이 한 줄이 "메시지가 오는가"를 판정합니다.

`OnGuardTimer()`에서 명령을 실행할 때도 기록하십시오.

```cpp
Log(L"popup", L"poll invoke row=%d", row);
```

이 로그들로 다음 회차에는 추측 없이 판정할 수 있습니다.

### 3-4. CPU 과다 사용을 조사한다 (필수, 별건)

이번 재현에서 별도의 이상이 확인되었습니다. 실행 약 40초 시점에 누적 CPU 시간이 **86초**였습니다. 코어 두 개를 계속 점유했다는 뜻입니다. 유휴 상태 목표치인 0.1% 미만과 크게 어긋납니다.

메뉴가 열린 동안에도 이 상태였으므로, 메뉴 문제와 별개로 상주 경로 어딘가가 바쁘게 돌고 있습니다. 다음 순서로 좁히십시오.

1. 프로그램을 실행하고 아무 조작도 하지 않은 채 60초 두십시오. 그 뒤 작업 관리자나 `Get-Process bamti | Select-Object CPU`로 누적 CPU 시간을 확인하십시오. 정상이라면 1초 미만이어야 합니다.
2. 값이 크면 어느 스레드인지 확인하십시오. PowerShell로 스레드별 누적 시간을 볼 수 있습니다.

   ```powershell
   (Get-Process bamti).Threads |
     Sort-Object { $_.TotalProcessorTime } -Descending |
     Select-Object -First 5 Id, ThreadState, WaitReason,
       @{n='CPU';e={$_.TotalProcessorTime.TotalSeconds}}
   ```
3. UI 스레드가 아니라면 `PipeServer`의 리슨 스레드가 유력합니다. `ListenLoop()`와 `ClientLoop()`에서 대기 없이 회전하는 경로가 없는지 확인하십시오. 특히 `ConnectNamedPipe`나 `WaitForMultipleObjects`가 즉시 반환될 때 곧바로 다시 시도하는 구조인지 보십시오.
4. UI 스레드라면 어떤 타이머나 메시지가 반복되는지 확인하십시오. 확인만 하고, 원인이 이번 팝업 수정 범위 밖이면 **고치지 말고 결과만 보고하십시오.** 별도 지시서로 다루겠습니다.

## 4. 하지 말아야 할 것

- `UpdateWindow()` 관련 수정을 되돌리지 마십시오. 0장의 로그가 효과를 입증합니다.
- `Open()`에 `target_.Reset()`을 다시 넣지 마십시오.
- `WH_MOUSE_LL`이나 `WH_KEYBOARD_LL`을 도입하지 마십시오. 2장에 적은 대로 이번 회차에서는 제외합니다.
- `SetForegroundWindow`와 `AttachThreadInput`을 도입하지 마십시오.
- `WS_EX_NOACTIVATE`를 떼지 마십시오. 이를 떼면 메뉴를 열 때 포커스를 빼앗아, 원래 고치려던 문제로 되돌아갑니다.
- `Handle()`의 기존 마우스 메시지 처리를 삭제하지 마십시오. 폴링과 병행합니다.
- `spotlight.cpp`와 `spotlight.hpp`의 미커밋 수정을 건드리지 마십시오.
- 3-4에서 원인을 찾더라도 팝업 범위 밖이면 고치지 마십시오. 보고만 하십시오.

## 5. 검증

**입력 (핵심)**
- [ ] 메뉴 항목 위로 커서를 옮기면 강조가 따라온다.
- [ ] `모두 보기`를 클릭하면 실제로 실행되고 메뉴가 닫힌다. 로그에 `[dock] menu cmd=4 show-all`이 남는다.
- [ ] 창 목록 항목을 클릭하면 해당 창이 활성화된다.
- [ ] `고정 해제`가 동작한다.
- [ ] 구분선이나 여백을 클릭하면 메뉴가 닫히지 않고 그대로 있다.
- [ ] 항목 위에서 누른 뒤 팝업 **밖으로** 끌고 나가서 떼면 아무 명령도 실행되지 않고 메뉴가 남는다.

**닫힘**
- [ ] 바탕화면 클릭, 다른 앱 클릭, `ESC`, `Alt+Tab`, `Win` 키에서 각각 닫힌다.
- [ ] 닫힐 때마다 `[popup] dismiss reason=...`이 남고 사유가 조작과 일치한다.
- [ ] `모두 보기` 실행 **직후** 다른 아이콘을 우클릭해도 정상으로 뜨고 조작된다. 이번 재현의 핵심 조건입니다.
- [ ] 메뉴를 연속 다섯 번 열고 닫아도 매번 정상이다.

**표시 (회귀)**
- [ ] `[popup] open ... shown` 값이 16ms 이하를 유지한다.
- [ ] 메뉴를 열 때 `[popup] create render target`이 찍히지 않는다.

**성능**
- [ ] 3-4의 측정 결과를 보고한다. 수정 여부와 무관하게 수치를 남긴다.
- [ ] 메뉴가 열려 있는 동안 CPU 점유가 눈에 띄게 오르지 않는다. 50ms 폴링에 렌더가 딸려 붙으면 오를 수 있으므로 3-2의 "변화가 있을 때만 그리기"를 확인하십시오.

**빌드**
- [ ] Release 빌드가 `/W4` 경고 없이 통과한다.
- [ ] 상단바 상태 항목 팝업 패널도 같은 `PopupSurface`를 쓰므로 함께 확인한다.
