# 작업 지시서: 열린 패널의 값 갱신과 설정 저장 경합

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

4단계 구현물을 사용하면서 드러난 결함 두 개를 고치는 지시서입니다. 서로 다른 파일이므로 커밋도 나눕니다.

| 결함 | 위치 | 발견 경로 |
|---|---|---|
| 1. 열려 있는 패널의 값이 갱신되지 않습니다 | `src/menu_bar.cpp` | 사용자가 화면에서 확인했습니다. |
| 2. 설정 저장이 겹치면 마지막 값이 남지 않습니다 | `src/widgets/builtin.cpp` | 검수 중 코드에서 확인했습니다. |

---

## 1. 결함 1: 패널이 열린 순간의 값에 멈춘다

**증상**: 위젯을 눌러 패널을 열면 그 순간의 숫자는 맞습니다. 그런데 패널을 열어 둔 채 기다려도 숫자가 그대로입니다. CPU 사용률이 5초마다, 네트워크 속도가 2초마다 바뀌는데 패널은 처음 값을 계속 보여 줍니다.

**원인**: 패널 내용이 열 때 한 번 복사되고, 그 뒤로 아무도 다시 넣어 주지 않습니다.

`MenuBar::OpenStatusPanel`은 스냅숏에서 항목을 찾아 `status_panel_->Reset(*found, ...)`으로 **복사본**을 넘깁니다. `StatusPanelContent`는 그 복사본(`item_`)을 그려 줍니다. 이후 공급자가 새 값을 `Upsert`하면 레지스트리가 `kStatusChangedMsg`를 보내지만, 그 처리는 다음이 전부입니다.

```cpp
case kStatusChangedMsg:
  NotePostedStorm(L"status", g_status_msg_count, g_status_msg_window);
  ArmRepaint();          // 상단바만 다시 그린다
  return 0;
```

`ArmRepaint`에서 이어지는 `RefreshLayout`은 바의 세그먼트만 다룹니다. 팝업은 별도의 창이고 별도의 콘텐츠 객체이므로 손대지 않습니다. 그래서 패널은 열릴 때의 값에 멈춥니다.

이것은 위젯만의 문제가 아닙니다. 파이프 클라이언트의 패널도 똑같이 멈춥니다. 명세는 `panel_open` 이후에도 클라이언트가 값을 계속 밀어 넣을 수 있다고 정하고 있으므로, 이 결함은 프로토콜 전체에 걸립니다.

### 1-1. 고치는 방법

`OnToggleTimeout` 안에 **이미 필요한 코드가 있습니다.** 토글이 되돌려질 때 열린 패널을 다시 채우는 블록입니다. 이것을 함수로 빼서 두 곳에서 함께 쓰십시오. 새 방식을 만들지 말고 있는 것을 옮기는 작업입니다.

```cpp
void MenuBar::RefreshOpenPanel();
```

동작 순서입니다.

1. `status_popup_.IsOpen()`이 거짓이거나, `open_panel_id_`가 비었거나, `status_panel_`이 없으면 아무것도 하지 않습니다.
2. `status_.Get(open_panel_id_)`로 최신 항목을 얻습니다. **없으면 팝업을 닫습니다.** 설명하던 대상이 사라졌는데 껍데기를 남겨 둘 이유가 없습니다. 항목에 `panel`이 없어진 경우도 같습니다.
3. `revision`이 마지막으로 반영한 값과 같으면 아무것도 하지 않고 돌아갑니다. 다른 항목이 갱신되어 들어온 통지에 헛일을 하지 않기 위해서입니다.
4. 패널의 행 개수가 열 때와 다르면 **팝업을 닫습니다.** 이유는 1-2절에 있습니다.
5. `status_panel_->Reset(std::move(*item), MakePanelHost())`를 부르고, `InvalidateRect(status_popup_.hwnd(), nullptr, FALSE)`로 다시 그립니다.

부를 곳은 두 군데입니다.

- `kStatusChangedMsg` 처리에서 `ArmRepaint()`와 나란히 부릅니다.
- `OnToggleTimeout`의 기존 블록을 이 함수 호출로 바꿉니다.

`StatusPanelHost`를 만드는 코드가 지금 `OpenStatusPanel`과 `OnToggleTimeout` 두 곳에 똑같이 있고 이번에 세 번째가 생깁니다. `MakePanelHost()` 같은 private 헬퍼 하나로 합쳐 주십시오. 이 정리는 이번 수정이 만들어 내는 중복을 없애는 것이므로 범위 안입니다. 그 밖의 정리는 하지 마십시오.

### 1-2. 크기는 바꾸지 않는다

`PopupSurface::Open`은 `content_->Measure(dpi)`를 **열 때 한 번만** 부르고 그 크기로 창을 만듭니다. 값을 갱신할 때 다시 재지 마십시오. 두 가지 이유가 있습니다.

1. 커서가 팝업 안에 있는 동안 창 크기가 2초마다 흔들리면 쓸 수 없는 UI가 됩니다. 전송 속도 문자열은 `980/12K`와 `1.2M/120K` 사이를 계속 오갑니다.
2. 폭이 모자라는 문자열은 이미 처리됩니다. `popup_surface.cpp`의 텍스트 레이아웃이 `CreateEllipsisTrimmingSign`으로 말줄임을 붙이므로 넘치지 않고 잘립니다.

행 개수가 달라지는 경우만 다릅니다. 행이 늘면 창 밖으로 벗어나 아예 보이지 않으므로, 그때는 갱신하지 말고 팝업을 닫습니다. 내장 위젯은 행 개수가 고정이라 이 경로를 타지 않고, 파이프 클라이언트가 패널 구조를 바꿀 때만 해당합니다.

행 개수와 `revision`을 기억할 멤버 두 개를 `OpenStatusPanel`에서 채워 두십시오.

### 1-3. 토글의 낙관적 갱신을 깨뜨리지 마십시오

**이 절을 빠뜨리면 이미 고친 결함이 되살아납니다.**

스위치를 누르면 `StatusPanelContent::Activate`가 `item_`의 행을 즉시 뒤집습니다. 이 뒤집힌 상태는 **패널 콘텐츠 안에만** 있고 레지스트리에는 없습니다. 클라이언트가 응답할 때까지 2초 동안 그렇습니다.

그런데 그사이에 아무 항목이나 갱신되면 `kStatusChangedMsg`가 오고, 위에서 만든 `RefreshOpenPanel`이 레지스트리의 값으로 콘텐츠를 다시 채웁니다. 그러면 **사용자가 방금 누른 스위치가 저절로 되돌아갑니다.** 내장 위젯이 2초마다 갱신되므로 이 상황은 반드시 일어납니다.

그래서 다음 조건을 넣습니다.

> `toggle_armed_`가 참인 동안에는, 항목의 `revision`이 `pending_toggle_.revision`과 **다를 때만** 갱신합니다.

`revision`이 그대로라는 것은 클라이언트가 아직 응답하지 않았다는 뜻이므로 낙관적 상태를 지킵니다. `revision`이 달라졌다면 응답이 온 것이므로 그 값으로 덮어쓰는 것이 맞습니다. 되돌리기 시한이 지나면 `OnToggleTimeout`이 `Upsert`로 `revision`을 올리므로 그 경로도 정상적으로 반영됩니다.

### 1-4. 오버플로 팝업은 이번에 고치지 않습니다

`OpenOverflow`도 `overflow_panel_->Reset(layout_.last().overflow, ...)`으로 목록을 한 번 복사하는 같은 구조입니다. 열어 둔 동안 값이 멈출 것으로 보입니다. 다만 오버플로는 항목이 들고 나면서 행 자체가 바뀌므로 판단할 것이 더 많고, 이번 보고에 포함된 증상도 아닙니다. **손대지 마십시오.** 별도로 다룹니다.

## 2. 결함 2: 설정 저장이 겹치면 마지막 값이 남지 않는다

**증상**: 위젯을 빠르게 여러 번 토글하면 로그에 `failed to write settings.json`이 여러 줄 남고, 마지막으로 누른 값이 파일에 반영되지 않을 수 있습니다.

**원인**: 두 가지가 겹칩니다.

1. `SubmitSave`는 토글할 때마다 스레드 풀에 작업을 **새로** 던지고, 서로를 기다리지 않습니다.
2. `WriteFileUtf8Atomic`은 고정된 `settings.json.tmp` 하나를 `dwShareMode = 0`으로 엽니다.

그래서 저장 두 개가 겹치면 뒤에 온 쪽의 `CreateFileW`가 실패합니다. 게다가 스레드 풀 콜백의 실행 순서는 제출 순서와 무관하므로, **겹치는 상황에서는 마지막에 누른 값이 아닌 값이 파일에 남을 수 있습니다.**

### 2-1. 고치는 방법

작업을 여러 개 던지지 말고, **최신 설정을 담는 슬롯 하나와 세대 번호**를 두어 한 번에 하나만 쓰게 합니다.

- `SetSettings`에서: 잠금 안에서 `pending_save_ = next; ++save_gen_;` 그리고 저장 작업이 돌고 있지 않을 때만 `save_busy_ = true`로 표시하고 작업을 하나 제출합니다. 이미 돌고 있으면 제출하지 않습니다. 슬롯에 최신 값이 들어갔으므로 돌고 있는 작업이 그것을 집어 갑니다.
- 콜백에서: 반복문으로 처리합니다. 잠금 안에서 `pending_save_`와 그때의 세대 번호를 꺼내고, 잠금을 풀고 `SaveWidgetSettings`를 부릅니다. 쓰기가 끝난 뒤 다시 잠그고, 세대 번호가 그사이 올라갔으면 한 번 더 돌고, 그대로면 `save_busy_ = false`로 내리고 `save_idle_event_`를 올린 뒤 끝냅니다.

이렇게 하면 두 가지가 함께 보장됩니다. 파일을 쓰는 스레드는 언제나 하나뿐이므로 `.tmp` 충돌이 없고, 마지막에 누른 값이 반드시 마지막으로 써집니다.

`.tmp` 파일 이름을 매번 다르게 만드는 방식으로 우회하지 마십시오. 충돌은 사라지지만 어느 값이 마지막에 남을지는 여전히 알 수 없습니다.

`Stop()`이 `save_idle_event_`를 최대 2초 기다리는 동작은 그대로 둡니다. 반복문이 한 번 더 도는 경우까지 포함해도 이 시간 안에 끝납니다.

### 2-2. 덤으로 줄어드는 것

지금은 토글할 때마다 스레드 풀 작업이 하나씩 늘어서, 100번 토글하면 스레드가 15개에서 83개까지 늘었다가 2분쯤 뒤에 돌아옵니다. 작업을 하나로 합치면 이 부풀림도 함께 사라집니다. 검증 항목에 넣어 두었습니다.

## 3. 하지 말아야 할 것

1. 팝업 콘텐츠를 갱신하려고 팝업을 닫았다 다시 열지 마십시오. 커서 아래에서 창이 깜빡이고 호버 상태가 날아갑니다.
2. 값이 바뀔 때마다 `Measure`를 다시 불러 창 크기를 조정하지 마십시오. 1-2절의 이유입니다.
3. 낙관적 토글 상태를 레지스트리에 미리 써 넣는 방식으로 1-3절을 우회하지 마십시오. 클라이언트가 응답하지 않았는데 응답한 것처럼 보이게 됩니다.
4. `StatusPanelContent`가 항목을 복사하지 않고 포인터로 참조하게 바꾸지 마십시오. 레지스트리의 값은 작업자 스레드가 바꾸므로 UI가 그리는 도중에 뒤집힙니다.
5. 오버플로 팝업을 고치지 마십시오(1-4절).
6. `settings.cpp`를 고치지 마십시오. 결함 2는 호출하는 쪽의 문제입니다.

## 4. 검증

**빌드**
- [ ] `/W4` 경고 없이 Debug와 Release가 빌드됩니다.

**결함 1**
- [ ] CPU 패널을 열어 두고 15초를 기다리면 숫자가 최소 두 번 바뀝니다.
- [ ] 네트워크 패널을 열어 두고 파일을 내려받으면 속도가 따라 움직입니다.
- [ ] 패널이 열려 있는 동안 창 크기가 변하지 않습니다.
- [ ] 패널을 열어 둔 채 그 위젯을 우클릭 메뉴에서 끄면 팝업이 닫힙니다.
- [ ] 패널 위에서 마우스를 올린 행의 강조 표시가 갱신 때문에 사라지지 않습니다.

**결함 1의 회귀 (토글)**
- [ ] `examples/ticker.py`처럼 토글 행이 있는 클라이언트의 패널을 열고, **내장 위젯 세 개를 모두 켠 상태에서** 스위치를 누릅니다. 클라이언트가 응답할 때까지 스위치가 눌린 상태를 유지합니다. 위젯 갱신 때문에 되돌아가면 안 됩니다.
- [ ] 클라이언트가 응답하지 않으면 2초 뒤에 스위치가 되돌아가고 항목이 `error`로 표시됩니다.
- [ ] 스위치 한 번 누름에 `toggle` 이벤트가 한 번만 갑니다.

**결함 2**
- [ ] 위젯을 100번 빠르게 토글한 뒤 로그에 `failed to write settings.json`이 한 줄도 없습니다.
- [ ] 그 직후 `settings.json`의 값이 마지막으로 누른 상태와 일치합니다.
- [ ] 100회 토글 직후 스레드 수가 크게 늘지 않습니다. 이전에는 15에서 83까지 늘었습니다.
- [ ] 토글한 직후 bamti를 종료하고 다시 실행해도 그 값이 남아 있습니다.

**남은 4단계 검증 하나**
- [ ] 폭이 부족할 때 항목이 갈매기 표시 안으로 접히는 것을 확인합니다. 이 모니터는 3413px이고 파이프 수신 인스턴스는 한 번에 하나뿐이라, 항목 개수만으로는 폭을 넘기지 못합니다. **바 텍스트를 32자로 꽉 채운 항목 16개**를 올리면 넘길 수 있습니다. 갈매기가 나타나는지, 눌렀을 때 접힌 항목이 우선순위 순서로 나오는지 확인해 주십시오.
