# 작업 지시서: 드래그 중 Ctrl 판정을 훅 사건이 아니라 실제 키 상태로 바꾸고, 반응을 빠르게 한다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

`FIX-SHOW-DESKTOP-SFALSE.md`(커밋 `b6b3b70`)의 후속입니다. 건드리는 파일은 `src/menu_bar.cpp`와 `src/menu_bar.hpp`입니다.

사용자가 확인한 것이 셋입니다. 첫째, Ctrl을 누른 채 코너에 계속 두어도 깜빡이지 않습니다(고칠 것 없음). 둘째, 전환이 느리고 끊깁니다. 셋째, **드래그 중에는 원래 창으로 돌아오지 못합니다.**

---

## 1. 드래그 중에 실패하는 이유 (측정)

사용자가 드래그로 시험한 구간의 로그입니다.

```
09:09:11.388 [peek] watch on=1
09:09:11.721 [peek] watch on=0      ← 333밀리초 뒤
09:09:12.302 [peek] watch on=1
09:09:12.496 [peek] watch on=0      ← 194밀리초 뒤
```

**토글이 한 번도 불리지 않았습니다.** 뜸이 300밀리초인데 감시가 그 전에 꺼졌기 때문입니다.

`watch on=0`을 찍는 곳은 `StopCornerWatch` 하나뿐이고, 그것을 부르는 곳도 `kCornerWatchMsg`를 `wparam == 0`으로 받는 자리 하나뿐입니다. 그리고 그 메시지를 보내는 곳은 저수준 키보드 훅의 **Ctrl 뗌** 갈래뿐입니다.

즉 **훅이 Ctrl 뗌을 보았습니다.** 사용자는 계속 누르고 있었다고 합니다.

둘 중 하나입니다.

1. 드래그 중에 어딘가에서 Ctrl 뗌 사건이 만들어진다.
2. 사용자가 실제로 잠깐 뗐다.

**어느 쪽인지 지금 가리려 하지 마십시오.** 어느 쪽이든 고칠 방법이 같고, 그 방법이 더 옳습니다.

---

## 2. 고치는 원칙: 기억이 아니라 실제 키 상태를 본다

이 프로젝트에서 같은 실수를 이미 한 번 했습니다. `peek_ctrl_`이라는 기억을 판정 근거로 삼았다가 낡은 값 때문에 화면이 번쩍였고, `GetAsyncKeyState`를 매번 읽도록 고쳐서 해결했습니다(`FIX-PEEK-CTRL-STALE.md`).

지금은 **감시를 끄는 판정이 훅 사건이라는 기억에 매여 있습니다.** 같은 방식으로 고칩니다.

### 2-1. 훅은 켜기만 한다

`LowLevelKeyboardProc`의 Ctrl 갈래에서 **뗌일 때 보내던 `wparam = 0` 메시지를 없애십시오.** 누름일 때 보내는 `wparam = 1`만 남깁니다.

훅은 감시를 시작시키는 방아쇠일 뿐이고, 끝내는 판단은 하지 않습니다.

**Ctrl을 삼키지 않는 것은 그대로 지키십시오.** 반드시 `CallNextHookEx`의 반환값으로 빠져나가야 합니다.

### 2-2. 감시 타이머가 스스로 끝낸다

`kCornerWatchTimerId` 처리부의 맨 앞에 다음을 넣으십시오.

```cpp
if ((GetAsyncKeyState(VK_CONTROL) & 0x8000) == 0) {
  StopCornerWatch();
  return 0;
}
```

`GetAsyncKeyState`는 실제 키 상태를 돌려주므로, 가짜 뗌 사건이 있었더라도 물리적으로 눌려 있는 한 감시가 살아 있습니다. 반대로 진짜로 뗐으면 한 틱 안에 꺼집니다.

`StopCornerWatch`는 그대로 두되, `kCornerWatchMsg`의 `wparam == 0` 갈래는 지웁니다.

### 2-3. 감시가 영원히 도는 것을 막는다

훅이 누름을 놓치는 경우는 없지만, 켠 뒤 어떤 이유로도 꺼지지 않는 일이 없도록 **감시 타이머가 스스로 끝내는 경로가 2-2 하나뿐**임을 확인하십시오. `GetAsyncKeyState`가 거짓을 돌려주면 반드시 꺼집니다.

---

## 3. 반응을 빠르게 한다

지금 사용자가 코너에 닿고 나서 창이 접히기까지 우리 쪽에서만 최대 360밀리초가 듭니다.

| 몫 | 지금 | 바꿀 값 |
| --- | --- | --- |
| 뜸(`kDesktopPeekDwellMs`) | 300 | **120** |
| 코너 감시 주기(`kCornerWatchMs`) | 60 | **30** |
| 합계(최악) | 360 | **150** |

이 둘만 줄이십시오. 감시는 Ctrl을 누르고 있는 동안에만 돌므로 30밀리초 주기여도 놀고 있을 때의 비용은 그대로 0입니다.

뜸을 더 줄이지는 마십시오. 120밀리초 아래로 내려가면 코너를 스쳐 지나갈 때도 발동합니다.

---

## 4. 끊기듯 전환되는 것은 우리 몫이 아니다

**창이 하나씩 접히는 애니메이션은 Windows가 그립니다.** 우리는 `MinimizeAll`을 부를 뿐이고 그리는 주체가 explorer이므로 코드로 부드럽게 만들 수 없습니다.

이 컴퓨터의 설정을 확인했습니다.

```
HKCU\Control Panel\Desktop\WindowMetrics\MinAnimate = 1   (애니메이션 켜짐)
```

이 값이 0이면 창이 즉시 접히고 펴집니다. **그러나 이것은 사용자의 시스템 설정이므로 코드로 바꾸지 마십시오.** 임시로 껐다 켜는 것도 하지 마십시오. 도중에 앱이 죽으면 사용자 설정이 꺼진 채로 남습니다.

**이 절에서는 아무것도 구현하지 마십시오.** 3절만 하고, 애니메이션은 사용자가 직접 판단할 수 있게 보고에만 적으십시오.

---

## 5. 진단을 남긴다

3절과 2절을 적용해도 드래그 중에 안 되면 다음 단서가 필요합니다.

1. **훅이 보는 Ctrl 사건**: 누름과 뗌마다 한 줄. `vk`, `wparam`(`WM_KEYUP`인지 `WM_SYSKEYUP`인지), `info->flags`, 그리고 **그 순간의 `GetAsyncKeyState(VK_CONTROL)`** 을 함께 남기십시오. 뗌 사건이 왔는데 실제 키는 눌려 있다면 가짜 사건이 있다는 증거가 됩니다.
2. **코너 진입과 이탈**: 매 틱이 아니라 **상태가 바뀔 때만** 한 줄. 커서 좌표와 상단바 사각형의 오른쪽 끝 값을 함께 남기십시오.
3. 뜸이 걸릴 때와 터질 때 각각 한 줄.

**매 30밀리초마다 로그가 쌓이면 안 됩니다.** 반드시 전이에서만 남기십시오.

---

## 6. 검증

이 환경에서는 마우스와 키보드 입력을 합성할 수 없습니다. **사용자 화면에 입력을 밀어 넣으려고 하지 마십시오.**

1. Release 클린 빌드가 경고 없이 통과해야 합니다.
2. **Ctrl+C와 Ctrl+V가 그대로여야 합니다.** 훅을 건드리므로 이것부터 확인하십시오.
3. `kCornerWatchMsg`를 `wparam=0`으로 보내는 곳이 코드에 남아 있지 않아야 합니다.
4. 감시 타이머가 Ctrl을 누르지 않은 상태에서는 돌지 않아야 합니다.
5. 나머지(드래그 중 동작, 전환 속도 체감)는 코드 경로를 설명하고 사용자 확인으로 넘기십시오.
6. 4절의 `MinAnimate` 이야기를 보고에 한 문단으로 적으십시오. **레지스트리에 쓰지 마십시오.**
