# 작업 지시서: 드래그 도중에 Ctrl을 눌러도 코너 감시가 시작되게 한다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

`FIX-RESTORE-ACTIVE-WINDOW.md`(커밋 `4212d20`)의 후속입니다. 건드리는 파일은 `src/menu_bar.cpp`와 `src/menu_bar.hpp`입니다.

---

## 1. 증상

사용자가 두 경우를 구분해 보고했습니다.

| 순서 | 결과 |
| --- | --- |
| Ctrl을 먼저 누르고 → 드래그 시작 → 코너 | **된다** |
| 드래그를 먼저 시작하고 → Ctrl 누름 → 코너 | **안 된다** |

차이는 **코너 감시가 언제 시작되어야 하는가** 하나뿐입니다. 앞의 경우에는 드래그가 시작되기 전에 이미 감시가 돌고 있고, 뒤의 경우에는 드래그 도중에 새로 시작되어야 합니다.

---

## 2. 무엇은 확실하고 무엇은 모르는가

**확실한 것: 드래그 도중에도 우리 타이머는 정상으로 돕니다.**

Ctrl을 먼저 누른 경우가 동작한다는 사실이 곧 증거입니다. 그 경우 코너를 찾아내는 것은 30밀리초 감시 타이머이고, 그 타이머는 드래그가 시작된 뒤에도 계속 돌아 `corner in=1`을 찍고 전환까지 마칩니다. **상단바 스레드의 메시지 처리는 드래그에 막히지 않습니다.**

**모르는 것: 드래그 도중에 저수준 키보드 훅이 Ctrl 누름을 전달하는가.**

지금 감시를 시작시키는 유일한 방아쇠가 `LowLevelKeyboardProc`의 Ctrl 누름 전이입니다. 이것이 드래그 중에 오지 않으면 감시가 시작되지 않고, 증상이 정확히 그렇습니다.

전달되지 않는 이유가 훅 자체인지, 아니면 `g_ctrl_held`가 이전 드래그에서 뗌을 놓쳐 참으로 굳은 탓에 전이가 생기지 않는 것인지는 **확정하지 못했습니다.**

**두 갈래를 가리려 하지 마십시오.** 아래 고침이 어느 쪽이든 해결합니다.

---

## 3. 고칠 것

### 3-1. 느린 예비 감시를 둔다

훅에만 의존하지 말고, **실제 키 상태를 주기적으로 확인해 감시를 시작하는 경로**를 하나 더 둡니다. 2절에서 확인했듯 타이머는 드래그 중에도 돌기 때문에 이 경로는 확실히 동작합니다.

```cpp
constexpr UINT_PTR kCtrlPollTimerId = 9;
constexpr UINT kCtrlPollMs = 200;
```

기존 타이머 아이디가 8까지 쓰이고 있으므로 9가 비어 있습니다. 확인하고 쓰십시오.

- 창이 만들어질 때 이 타이머를 걸고, `WM_DESTROY`에서 죽입니다. **항상 돕니다.**
- 매번 하는 일은 다음 두 줄이 전부입니다.

```cpp
if ((GetAsyncKeyState(VK_CONTROL) & 0x8000) != 0 && !corner_watch_on_) {
  StartCornerWatch();
}
```

`GetAsyncKeyState`와 깃발 하나를 읽는 것이라 200밀리초에 한 번이면 비용이 사실상 없습니다. **훅은 그대로 두십시오.** 훅이 오는 경우에는 즉시 시작되고, 오지 않는 경우에만 최대 200밀리초 뒤에 이 경로가 대신 시작합니다.

**로그를 남기지 마십시오.** 200밀리초마다 도는 자리입니다. `StartCornerWatch`가 이미 시작될 때만 한 줄 남기므로 그것으로 충분합니다.

### 3-2. 굳은 `g_ctrl_held`를 스스로 풀게 한다

감시 타이머가 `GetAsyncKeyState`로 Ctrl이 떨어진 것을 확인하고 `StopCornerWatch`를 부르는 자리가 이미 있습니다. **그 자리에서 `g_ctrl_held`도 함께 거짓으로 되돌리십시오.**

`g_ctrl_held`는 지금 익명 이름 공간의 전역이므로, `MenuBar`에서 닿을 수 있게 파일 안에서 접근하면 됩니다. 새 함수를 만들지 말고 대입 한 줄이면 충분합니다.

이렇게 하면 훅이 뗌을 놓쳐 굳더라도 다음 감시 종료에서 저절로 풀립니다. **이 프로젝트에서 네 번째로 같은 원칙을 적용하는 것입니다. 기억이 아니라 실제 키 상태가 권위입니다.**

---

## 4. 하지 말 것

- **`WH_MOUSE_LL` 마우스 훅을 새로 걸지 마십시오.** 키보드 훅이 드래그 중에 오지 않는 것이라면 마우스 훅도 같은 처지일 수 있고, 모든 마우스 이동마다 우리 코드가 끼어들면 시스템 전체가 느려집니다.
- 훅 안에서 로그를 부르지 마십시오. 이전에 UI 스레드를 막아 문제가 됐습니다.
- 걸쇠(`peek_latched_`), 뜸(120밀리초), 감시 주기(30밀리초), 코너 폭(14 DIP)을 건드리지 마십시오.
- 예비 감시 주기를 200밀리초보다 짧게 하지 마십시오. 이 타이머는 항상 돌기 때문에 유휴 비용에 직접 영향을 줍니다.

---

## 5. 검증

1. Release 클린 빌드가 경고 없이 통과해야 합니다.
2. **Ctrl+C와 Ctrl+V**가 그대로여야 합니다.
3. `kCtrlPollTimerId`가 창 생성에서 걸리고 `WM_DESTROY`에서 죽는지 코드로 확인하십시오.
4. **예비 감시 자리에 로그가 없어야 합니다.** 로그 파일이 200밀리초마다 자라면 안 됩니다. 몇 분 띄워 두고 파일 크기가 늘지 않는 것을 확인하십시오.
5. Ctrl을 누르지 않은 상태에서 30밀리초 감시 타이머가 돌지 않아야 합니다. 예비 감시만 도는 것이 정상입니다.
6. 나머지(드래그 도중 Ctrl 누름)는 사용자 확인으로 넘기십시오. `watch on=1`이 찍히는지가 판정 근거입니다.

이 환경에서는 마우스와 키보드 입력을 합성할 수 없습니다. 사용자 화면에 입력을 밀어 넣으려고 하지 마십시오.

**빌드하려고 실행 중인 bamti를 종료했다면, 끝난 뒤 반드시 다시 띄워 놓으십시오.**

레지스트리에 쓰는 확인 절차는 넣지 마십시오.
