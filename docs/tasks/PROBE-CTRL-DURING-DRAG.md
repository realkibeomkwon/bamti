# 작업 지시서: 드래그 도중에 Ctrl이 보이지 않는 이유를 측정한다

> 작업 당시의 진단과 지시를 남긴 기록입니다. 현재 코드의 설명이 아닙니다.

`FIX-CTRL-DURING-DRAG.md`(커밋 `349aa48`)의 후속입니다. 건드리는 파일은 `src/menu_bar.cpp`와 `src/menu_bar.hpp`입니다.

**이 지시서는 탐침만 넣습니다. 동작을 고치지 마십시오.** 원인이 밝혀진 뒤에 별도 지시서로 고칩니다.

---

## 1. 지금까지 확인된 것

드래그를 먼저 시작한 뒤 Ctrl을 누르면 코너 전환이 되지 않습니다. 사용자가 그 동작을 한 구간(11:23:21 이후)의 로그에 **`[peek]` 줄이 한 개도 없습니다.**

두 경로가 모두 침묵했다는 뜻입니다.

1. 저수준 키보드 훅의 Ctrl 누름 전이 → `watch msg`가 없습니다.
2. 200밀리초 예비 감시의 `GetAsyncKeyState(VK_CONTROL)` → `watch on=1`이 없습니다.

**서로 독립적인 두 방법이 동시에 눈이 멀었습니다.** 반면 Ctrl을 먼저 누르고 드래그를 시작하면 30밀리초 감시 타이머가 드래그 내내 `GetAsyncKeyState`로 Ctrl이 눌린 것을 계속 확인하며 정상 동작합니다.

정리하면 이렇습니다.

| 상황 | 결과 |
| --- | --- |
| 드래그 시작 **전**부터 눌려 있던 Ctrl | 드래그 중에도 계속 보인다 |
| 드래그 시작 **후**에 누른 Ctrl | 훅에도 안 오고 `GetAsyncKeyState`에도 안 잡힌다 |
| 우리 타이머 자체 | 드래그 중에도 정상으로 돈다 |

**왜 그런지는 모릅니다.** 추측하지 말고 재십시오.

---

## 2. 무엇을 재는가

이미 있는 200밀리초 예비 감시 타이머(`kCtrlPollTimerId`) 안에서 한 묶음을 읽고, **직전 값과 달라졌을 때만** 한 줄 남깁니다.

```cpp
[peek] probe hook=%u async_c=%d async_l=%d async_r=%d keystate_c=%d lbtn=%d
              capture=%p guiflags=0x%08lx fg=%p lastinput=%lu
```

| 항목 | 무엇을 얻는가 |
| --- | --- |
| `hook` | 훅이 지금까지 본 키 이벤트의 누적 개수 |
| `async_c` / `async_l` / `async_r` | `GetAsyncKeyState`의 `VK_CONTROL`, `VK_LCONTROL`, `VK_RCONTROL` |
| `keystate_c` | `GetKeyState(VK_CONTROL)` |
| `lbtn` | `GetAsyncKeyState(VK_LBUTTON)`. 드래그 중인지 가리는 값이다 |
| `capture` | `GetGUIThreadInfo(0, ...)`의 `hwndCapture`. 드래그를 쥔 창이다 |
| `guiflags` | 같은 구조체의 `flags`. `GUI_INMOVESIZE` 따위가 켜지는지 본다 |
| `fg` | `GetForegroundWindow()` |
| `lastinput` | `GetLastInputInfo`의 `dwTime`. 시스템 전체에 입력이 들어오고 있는지 본다 |

### 2-1. 훅 계수기

`LowLevelKeyboardProc` 안에 **로그가 아니라 계수기만** 두십시오.

```cpp
volatile UINT g_hook_key_count = 0;
```

`code == HC_ACTION`이고 주입된 입력이 아닐 때 하나 올립니다. **훅 안에서 절대 로그를 부르지 마십시오.** 이전에 UI 스레드를 막아 문제가 됐습니다.

### 2-2. 변화가 있을 때만 남긴다

위 항목을 하나의 구조체나 문자열로 만들어 **직전 것과 같으면 남기지 않습니다.** 사용자가 가만히 있으면 로그가 자라지 않아야 합니다.

`lastinput`은 입력이 있을 때마다 바뀌므로, **비교 대상에서 빼고 값만 함께 출력하십시오.** 그러지 않으면 200밀리초마다 줄이 쌓입니다.

### 2-3. `GetGUIThreadInfo` 주의

`GUITHREADINFO`는 `cbSize`를 먼저 채워야 합니다. 실패하면 `capture`와 `guiflags`를 0으로 두고 계속 진행하십시오.

---

## 3. 이 탐침이 답할 것

사용자가 "드래그 시작 → Ctrl 누름 → 코너"를 한 번 하면 다음이 갈립니다.

1. **`hook` 값이 드래그 중에 멈춰 있다** → 훅에 키 이벤트가 아예 오지 않습니다. 시스템이 그 구간에 우리 훅을 건너뛰는 것입니다.
2. **`hook`은 오르는데 `async_c`가 0이다** → 훅은 오는데 우리 Ctrl 판정이 틀린 것입니다. `async_l`과 `async_r`을 따로 본 것이 여기서 쓰입니다.
3. **`hook`도 멈추고 `lbtn`도 0이다** → 드래그 중에 우리 프로세스가 입력 상태를 전혀 못 보는 것입니다. `lastinput`이 계속 오르고 있다면 시스템에는 입력이 들어오는데 우리만 못 보는 것이 확정됩니다.
4. **`capture`가 계속 0이다** → 우리가 드래그 자체를 관측하지 못하는 것이고, 다른 관측 수단을 찾아야 합니다.

각 갈래마다 다음 수가 다릅니다. **이번에는 재기만 하고 고치지 마십시오.**

---

## 4. 하지 말 것

- 동작을 바꾸지 마십시오. 걸쇠, 뜸, 감시 주기, 코너 폭, 예비 감시 주기 전부 그대로입니다.
- Raw Input을 등록하지 마십시오. 다음 단계의 후보이고 이번 범위가 아닙니다.
- `WH_MOUSE_LL`을 걸지 마십시오.
- 훅 안에서 로그를 부르지 마십시오. 계수기만입니다.
- `AttachThreadInput`을 쓰지 마십시오.

---

## 5. 검증

1. Release 클린 빌드가 경고 없이 통과해야 합니다.
2. **가만히 두었을 때 로그가 자라지 않아야 합니다.** bamti를 띄우고 아무것도 하지 않은 채 3분 두고, `probe` 줄이 몇 개 쌓이는지 세십시오. 한 자리 수여야 합니다.
3. 키를 몇 개 눌러 보면 `hook` 값이 오르고 `probe` 줄이 그때만 남아야 합니다.
4. `LowLevelKeyboardProc` 안에 `Log` 호출이 없어야 합니다.
5. 드래그 도중 관측은 사용자 확인으로 넘기십시오.

이 환경에서는 마우스와 키보드 입력을 합성할 수 없습니다. 사용자 화면에 입력을 밀어 넣으려고 하지 마십시오.

**빌드하려고 실행 중인 bamti를 종료했다면, 끝난 뒤 반드시 다시 띄워 놓으십시오.**

레지스트리에 쓰는 확인 절차는 넣지 마십시오.
